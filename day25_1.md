Here's what I found digging through both chapters. s08 and s09 are the two "long-horizon" chapters: **s08 keeps one session alive by managing context**, and **s09 carries knowledge *across* sessions by managing memory.** They're deliberately complementary.

## s08 — Context Compaction (within a session)

The problem: a coding agent's history grows without bound (huge tool results, long transcripts), and eventually it overflows the model's context window. s08 layers **four escalating strategies** in `ContextCompactor` (all budgets are in *characters*, a cheap proxy for tokens):

| Stage | Method | What it does |
|---|---|---|
| 1. Budget tool results | `tool_result_budget` / `persist_large_output` | Any single tool output > 30k chars is written to disk; the message keeps a `<persisted-output>` stub with a ~2k preview. |
| 2. Snip | `snip_compact` | If > 50 messages, keep the head + tail and replace the middle with a one-line marker `[N messages archived at <transcript.jsonl>]`. Splits are adjusted so a `tool_use` never gets separated from its `tool_result`. |
| 3. Micro / fit | `micro_compact` / `fit_tool_results` | Shrinks *consumed* tool results (all but the last 3) to `[Earlier tool result saved at …]`, then, if still too big, replaces the largest ones with truncated previews until under 80% of the limit. |
| 4. Full summary | `compact_history` | Writes a transcript, then asks the model to summarize the whole thing as *factual state* (goal, decisions, files, remaining work) and replaces history with a single "Compacted" message. |

Key details that make it robust:
- **`estimate_chars`** = `len(json.dumps(messages))` — the single size metric everything compares against `CONTEXT_CHAR_LIMIT = 50000`.
- **`prepare()`** runs every turn and cascades 1→4, only falling to the next stage if still over budget.
- **`unseen_tool_result_positions`** protects results the model hasn't seen yet (added since its last assistant turn) from being micro-compacted — you never throw away the answer to a tool call the model is about to read.
- **`reactive_compact`** is the safety net: if the API throws `prompt_too_long`, it keeps the last `KEEP_RECENT_MESSAGES` and summarizes the rest, then retries once.
- **The `compact` tool** lets the *model itself* request compaction between tool batches.
- **`summary_message`** wraps the summary in an explicit `[Compacted] … (reference only)` frame so the model treats it as data, not as a live instruction — a prompt-injection guard.

## s09 — Memory (across sessions)

s08 forgets when the session ends. s09 adds a persistent `.memory/` store and a cycle around the loop: **load → inject → converse → extract → consolidate**.

- **Named memory files** (glob of `.memory/*.md` style) with YAML frontmatter (type: user / feedback / project / reference, etc.). A `MEMORY_INDEX` lists them cheaply.
- **Selective recall** — `select_relevant_memories` / keyword scoring ranks stored memories against the current query and only injects the top ones under a `RECALL_CHAR_LIMIT`. This is the "selective knowledge" idea: don't dump everything, retrieve what's relevant.
- **Injection** — `load_memories(messages)` + `build_system(...)` prepend the selected memories to the system prompt at the *start of `agent_loop`*.
- **Extraction** — at the end of a turn (when there are no more tool calls), `extract_memories(messages)` asks the model what durable facts emerged (the `should_store_memory` gate decides if anything is worth writing), and writes/updates memory files.
- **Consolidation** — `consolidate_memories()` runs once a `CONSOLIDATE_THRESHOLD` is hit, merging/deduping memories so the store doesn't sprawl.

## How they fit together

- **s08 solves depth** — how to keep working inside one very long task without losing the thread (compress, archive, summarize).
- **s09 solves breadth** — how to remember *who the user is and what the project is* from session to session (store, select, reload).
- Both treat the model as the summarizer but wrap its output so it's treated as **reference data**, and both spill raw material to disk (transcripts / tool-results / memory files) so nothing is truly lost — only the *in-context* view shrinks.

A real product like Claude Code uses exactly this shape: context compaction for the live window, plus a memory/CLAUDE.md-style store for durable project facts.
