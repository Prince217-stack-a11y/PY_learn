```python
import os
from openai import OpenAI
from dotenv import load_dotenv

load_dotenv()

class HelloAgentsLLM:
    """调用任何兼容 OpenAI 接口的 LLM 服务。"""
    def __init__(self):
        self.model = os.getenv("LLM_MODEL_ID")
        self.client = OpenAI(
            api_key=os.getenv("LLM_API_KEY"),
            base_url=os.getenv("LLM_BASE_URL"),
        )

    def think(self, messages, temperature=0):
        """非流式调用，返回完整文本。"""
        response = self.client.chat.completions.create(
            model=self.model, messages=messages, temperature=temperature
        )
        return response.choices[0].message.content
```

## 3.1 ReAct：Reason + Act（第 4.2 节）

### 3.1.1 它解决了什么问题

ReAct 诞生前，主流方法分两类：
- **"纯思考"型**（如思维链 Chain-of-Thought）：能引导模型做复杂逻辑推理，但**无法与外部世界交互**，容易产生事实幻觉。
- **"纯行动"型**：模型直接输出要执行的动作，但**缺乏规划和纠错能力**。

ReAct（Shunyu Yao, 2022）由认识到**思考与行动相辅相成**：**思考指导行动，行动的结果又反过来修正思考。** 它通过特殊的提示工程引导模型，使每一步输出都遵循固定轨迹：

- **Thought（思考）**：智能体的"内心独白"——分析当前情况、分解任务、制定下一步计划，或反思上一步结果。
- **Action（行动）**：决定采取的具体动作，通常是调用外部工具，如 `Search['华为最新款手机']`。
- **Observation（观察）**：执行 `Action` 后从外部工具返回的结果。

### 3.1.2 核心循环与形式化

智能体不断重复 **Thought → Action → Observation** 循环，把新观察追加到历史记录，形成不断增长的上下文，直到在 `Thought` 中认为已找到最终答案。

形式化：在每个时间步 $t$，智能体的策略（即 LLM $\pi$）根据初始问题 $q$ 和之前所有"行动-观察"轨迹 $((a_1,o_1),\dots,(a_{t-1},o_{t-1}))$ 生成当前的思考 $th_t$ 和行动 $a_t$：

$$(th_t, a_t) = \pi\left(q, (a_1,o_1),\dots,(a_{t-1},o_{t-1})\right)$$

随后环境中的工具 $T$ 执行行动 $a_t$，返回新观察 $o_t$：$o_t = T(a_t)$。循环持续，直到模型在思考中判断任务完成。

> 协同效应：**推理使行动更具目的性，而行动则为推理提供了事实依据。**

### 3.1.3 适用场景

- **需要外部知识的任务**：查询实时信息（天气、新闻、股价）、搜索专业领域知识。
- **需要精确计算的任务**：把数学问题交给计算器，避免 LLM 计算错误。
- **需要与 API 交互的任务**：操作数据库、调用某个服务的 API。

本节实战目标："**华为最新的手机是哪一款？它的主要卖点是什么？**"——需要智能体理解自己需要上网搜索、调用工具搜索并总结答案。

### 3.1.4 工具的定义与实现

> 如果说大语言模型是智能体的**大脑**，那么**工具（Tools）就是其与外部世界交互的"手和脚"**。

**一个良好定义的工具应包含三个核心要素**：
1. **名称（Name）**：简洁、唯一的标识符，供智能体在 `Action` 中调用，例如 `Search`。
2. **描述（Description）**：清晰的自然语言描述，说明用途。**这是整个机制中最关键的部分**——大语言模型依赖这段描述判断何时使用哪个工具。
3. **执行逻辑（Execution Logic）**：真正执行任务的函数或方法。

**（1）实现搜索工具核心逻辑**（选用 SerpApi，提供结构化 Google 搜索结果）：


```python
from serpapi import SerpApiClient

def search(query: str) -> str:
    """基于 SerpApi 的实战网页搜索引擎工具，智能解析搜索结果，优先返回直接答案或知识图谱信息。"""
    print(f"🔍 正在执行 [SerpApi] 网页搜索: {query}")
    try:
        api_key = os.getenv("SERPAPI_API_KEY")
        if not api_key:
            return "错误：SERPAPI_API_KEY 未在 .env 文件中配置。"
        params = {"engine": "google", "q": query, "api_key": api_key,
                  "gl": "cn", "hl": "zh-cn"}          # 国家代码 / 语言代码
        client = SerpApiClient(params)
        results = client.get_dict()

        # 智能解析：优先寻找最直接的答案
        if "answer_box_list" in results:
            return "\n".join(results["answer_box_list"])
        if "answer_box" in results and "answer" in results["answer_box"]:
            return results["answer_box"]["answer"]
        if "knowledge_graph" in results and "description" in results["knowledge_graph"]:
            return results["knowledge_graph"]["description"]
        if "organic_results" in results and results["organic_results"]:
            # 没有直接答案时，返回前三个有机结果的摘要
            snippets = [
                f"[{i+1}] {res.get('title', '')}\n{res.get('snippet', '')}"
                for i, res in enumerate(results["organic_results"][:3])
            ]
            return "\n\n".join(snippets)
        return f"对不起，没有找到关于 '{query}' 的信息。"
    except Exception as e:
        return f"搜索时发生错误: {e}"
```

> **"智能解析"是精髓**：优先检查 `answer_box`（Google 答案摘要框）或 `knowledge_graph`（知识图谱），存在就直接返回这些最精确的答案；否则才退而求其次返回前三条常规搜索摘要。这种解析能为 LLM 提供质量更高的信息输入。

**（2）构建通用工具执行器 `ToolExecutor`**——当需要多种工具（搜索、计算、查数据库等）时，需要统一的管理器注册与调度：

```python
from typing import Dict, Any

class ToolExecutor:
    """一个工具执行器，负责管理和执行工具。"""
    def __init__(self):
        self.tools: Dict[str, Dict[str, Any]] = {}

    def registerTool(self, name: str, description: str, func: callable):
        """向工具箱中注册一个新工具。"""
        if name in self.tools:
            print(f"警告：工具 '{name}' 已存在，将被覆盖。")
        self.tools[name] = {"description": description, "func": func}
        print(f"工具 '{name}' 已注册。")

    def getTool(self, name: str) -> callable:
        return self.tools.get(name, {}).get("func")

    def getAvailableTools(self) -> str:
        """把工具名与描述格式化成文本，注入 System Prompt。"""
        return "\n".join([f"- {name}: {info['description']}"
                          for name, info in self.tools.items()])
```

### 3.1.5 ReAct 智能体的编码实现

ReAct 提示词模板的关键：**固定输出格式 + 工具清单 + 结束标记 + 轨迹示例**。

```python
REACT_PROMPT_TEMPLATE = """
请注意，你是一个有能力调用外部工具的智能助手。

可用工具如下：
{tools}

请严格按照以下格式进行回应：
Thought: 你的思考过程，用于分析问题、拆解任务和规划下一步行动。
Action: 你决定采取的行动，必须是以下格式之一：
- `{{tool_name}}[{{tool_input}}]`：调用一个可用工具。
- `Finish[最终答案]`：当你认为已经获得最终答案时。

现在，请开始解决以下问题：
Question: {question}
History: {history}
"""

class ReActAgent:
    def __init__(self, llm_client, tool_executor, max_steps=5):
        self.llm_client = llm_client
        self.tool_executor = tool_executor
        self.max_steps = max_steps
        self.history = []

    def run(self, question: str) -> str:
        self.history = []
        current_step = 0
        while current_step < self.max_steps:
            current_step += 1
            # ① 用工具描述与历史构造提示词
            prompt = REACT_PROMPT_TEMPLATE.format(
                tools=self.tool_executor.getAvailableTools(),
                question=question,
                history="\n".join(self.history),
            )
            # ② 调用 LLM
            response_text = self.llm_client.think(
                messages=[{"role": "user", "content": prompt}])
            # ③ 解析 Thought / Action
            thought, action = self._parse_output(response_text)
            if action is None:
                self.history.append(response_text)
                continue
            # ④ 判断是否结束
            if action.startswith("Finish"):
                return self._parse_action_input(action)
            # ⑤ 执行工具并把观察结果追加到历史
            tool_name, tool_input = self._parse_action(action)
            tool_func = self.tool_executor.getTool(tool_name)
            if tool_func:
                observation = tool_func(tool_input)
            else:
                observation = f"错误：未找到名为 '{tool_name}' 的工具。"
            self.history.append(f"Thought: {thought}")
            self.history.append(f"Action: {action}")
            self.history.append(f"Observation: {observation}")
        return "抱歉，我无法在限定步数内完成这个任务。"
```

### 3.1.6 ReAct 的特点、局限性与调试技巧（第 4.2.4 节）

- ✅ **核心优势：环境适应性 + 动态纠错能力**——处理探索性、需要外部工具输入的任务的首选。
- ⚠️ 依赖**正则解析** LLM 输出，脆弱（格式一变即失败）。
- ⚠️ 步数多时**上下文迅速膨胀**，Token 成本高。
- ⚠️ 可能**反复调用同一工具**陷入局部循环。
- 🛠️ 调试技巧：打印每一轮的 Thought/Action/Observation；先固定工具再调提示词；把失败案例的 history 存下来分析。

## 3.2 Plan-and-Solve：先规划后执行（第 4.3 节）

### 3.2.1 工作原理

由 Lei Wang（2023）提出，核心动机是解决**思维链在处理多步、复杂问题时容易"偏离轨道"**的问题。

> 类比：**ReAct 像经验丰富的侦探**——根据现场蛛丝马迹（Observation）一步步推理、随时调整调查方向；**Plan-and-Solve 像建筑师**——动工前必须先绘制完整蓝图（Plan），然后严格按蓝图施工（Solve）。

与 ReAct 将思考与行动融合在每一步不同，Plan-and-Solve 把整个流程**解耦为两个核心阶段**：
1. **规划阶段（Planning）**：接收完整问题，第一任务不是直接解决或调用工具，而是**把问题分解、制定出清晰、分步骤的行动计划**。这个计划本身就是一次 LLM 调用的产物。
2. **执行阶段（Solving）**：获得完整计划后，**严格按计划步骤逐一执行**。每步执行可能是一次独立的 LLM 调用，或对上一步结果的加工处理，直到所有步骤完成，得出最终答案。

"**先谋后动**"的策略，使智能体在处理需要长远规划的复杂任务时能保持更高的**目标一致性**，避免在中间步骤中迷失方向。

**形式化**：

$$P = \pi_{\text{plan}}(q), \qquad s_i = \pi_{\text{solve}}(q, P, (s_1,\dots,s_{i-1})), \qquad \text{最终答案}=s_n$$

### 3.2.2 适用场景

- **多步数学应用题**：先列出计算步骤，再逐一求解。
- **需要整合多个信息源的报告撰写**：先规划报告结构（引言、数据源 A、数据源 B、总结），再逐一填充。
- **代码生成任务**：先构思函数、类、模块结构，再逐一实现。

### 3.2.3 规划阶段的提示词（强制输出可解析格式）

本节的推理任务：*"一个水果店周一卖出了 15 个苹果。周二卖出的苹果数量是周一的两倍。周三卖出的数量比周二少了 5 个。请问这三天总共卖出了多少个苹果？"*
智能体需要：① 规划——将问题分解为三个独立计算步骤（周二销量、周三销量、总销量）；② 执行——严格按计划逐步计算，每步结果作为下一步输入，最终得出总和。

````python
PLANNER_PROMPT_TEMPLATE = """
你是一个顶级的AI规划专家。你的任务是将用户提出的复杂问题分解成一个由多个简单步骤组成的行动计划。
请确保计划中的每个步骤都是一个独立的、可执行的子任务，并且严格按照逻辑顺序排列。
你的输出必须是一个Python列表，其中每个元素都是一个描述子任务的字符串。

问题: {question}

请严格按照以下格式输出你的计划,```python与```作为前后缀是必要的:
```python
["步骤1", "步骤2", "步骤3", ...]
```
"""
````

### 3.2.4 执行器与状态管理

```python
from typing import List, Dict, Any
from ast import literal_eval
import re

class PlanAndSolveAgent:
    def __init__(self, llm_client, max_steps=5):
        self.llm_client = llm_client

    def run(self, question: str) -> str:
        # --- 阶段一：规划 ---
        planner_prompt = PLANNER_PROMPT_TEMPLATE.format(question=question)
        plan_text = self.llm_client.think(
            messages=[{"role": "user", "content": planner_prompt}])
        plan = self._parse_plan(plan_text)            # 解析成 Python 列表
        print(f"📋 制定计划: {plan}")

        # --- 阶段二：执行（带状态管理）---
        history = []                                   # 保存每步结果
        for i, step in enumerate(plan, 1):
            executor_prompt = EXECUTOR_PROMPT_TEMPLATE.format(
                question=question,
                plan="\n".join(f"{j+1}. {s}" for j, s in enumerate(plan)),
                history="\n".join(history) or "（暂无）",
                current_step=f"{i}. {step}",
            )
            result = self.llm_client.think(
                messages=[{"role": "user", "content": executor_prompt}])
            history.append(f"步骤{i}[{step}] 结果: {result}")
            print(f"✅ 步骤{i}完成: {result}")
        return history[-1]                             # 最后一步结果是最终答案

    def _parse_plan(self, text: str) -> List[str]:
        """从 LLM 输出中提取 Python 列表。"""
        match = re.search(r"```python\s*(.*?)\s*```", text, re.DOTALL)
        code = match.group(1) if match else text
        try:
            return literal_eval(code)
        except Exception:
            return [line.strip("- ").strip()
                    for line in text.splitlines() if line.strip()]
```

**执行器提示词要点**：明确"仅输出该步骤的最终答案，不要输出任何额外的解释或对话"，并要求参考"原始问题 + 完整计划 + 已完成步骤的结果"。

### 3.2.5 优缺点

- ✅ **结构性强、稳定性高、目标一致性好**——特别适合逻辑路径确定、内部推理密集的任务。
- ⚠️ 计划一旦制定较难动态调整；对问题的理解偏差会被放大到整条执行链。
- ⚠️ 步骤过多时，每步独立 LLM 调用会带来较高成本。

## 3.3 Reflection：执行-反思-优化（第 4.4 节）

### 3.3.1 核心思想

在已实现的 ReAct 与 Plan-and-Solve 中，智能体一旦完成任务，工作流程便告结束。但初始答案（行动轨迹或最终结果）都可能存在谬误或待改进之处。Reflection 的核心思想是为智能体引入一种**事后（post-hoc）的自我校正循环**，使它像人类一样审视自己的工作、发现不足、迭代优化。

灵感来源于人类学习过程：完成初稿后校对、解出数学题后验算。这一思想在多项研究中体现，例如 Shinn（2023）的 **Reflexion** 框架。核心是简洁的三步循环：**执行 → 反思 → 优化**。

1. **执行（Execution）**：用熟悉的方法（如 ReAct 或 Plan-and-Solve）尝试完成任务，生成初步解决方案或行动轨迹——"初稿"。
2. **反思（Reflection）**：调用独立（或带特殊提示词）的 LLM 实例扮演**"评审员"**，从多维度评估"初稿"：
   - **事实性错误**：是否存在与常识或已知事实相悖的内容？
   - **逻辑漏洞**：推理过程是否存在不连贯或矛盾？
   - **效率问题**：是否有更直接、更简洁的路径？
   - **遗漏信息**：是否忽略了问题的某些关键约束或方面？
   据此生成结构化的**反馈（Feedback）**，指出具体问题与改进建议。
3. **优化（Refinement）**：把"初稿 + 反馈"作为新上下文，再次调用 LLM，要求根据反馈修正初稿，生成更完善的"修订稿"。

循环可重复多次，直到反思阶段不再发现新问题，或达到预设迭代上限。

**形式化**：设 $O_i$ 是第 $i$ 次迭代的输出（$O_0$ 为初始输出），反思模型生成针对 $O_i$ 的反馈 $F_i$：

$$F_i = \pi_{\text{reflect}}(\text{Task}, O_i), \qquad O_{i+1} = \pi_{\text{refine}}(\text{Task}, O_i, F_i)$$

### 3.3.2 Reflection 的三点独有价值

- 提供**内部纠错回路**，不再完全依赖外部工具反馈（ReAct 的 Observation），从而能修正**更高层次的逻辑和策略错误**。
- 把一次性任务执行转变为**持续优化的过程**，显著提升复杂任务的最终成功率和答案质量。
- 为智能体构建临时的**"短期记忆"**：整个"执行-反思-优化"轨迹形成宝贵的经验记录——智能体不仅知道最终答案，还记得自己如何从有缺陷的初稿迭代到最终版本。进一步，这个记忆系统还可以是**多模态的**，允许反思和修正文本以外的输出（代码、图像等），为构建更强大的多模态智能体奠定基础。

### 3.3.3 案例设定与记忆模块设计

**目标任务**："编写一个 Python 函数，找出 1 到 n 之间所有的素数（prime numbers）。"

这个任务是检验 Reflection 的绝佳场景：
1. **存在明确的优化路径**：LLM 初次生成的代码很可能是简单但低效的递归实现。
2. **反思点清晰**：可通过反思发现"时间复杂度过高"或"存在重复计算"。
3. **优化方向明确**：可根据反馈优化为更高效的迭代版本或使用备忘录模式的版本。

Reflection 的核心在于**迭代**，而迭代的前提是**能记住之前的尝试和获得的反馈**。因此一个"短期记忆"模块是必需品——负责存储每一次"执行-反思"循环的完整轨迹。（若上下文足够长，让"评审员"直接获取所有信息再反思，往往会传入大量冗余。）

```python
from typing import List, Dict, Any, Optional

class Memory:
    """一个简单的短期记忆模块，用于存储智能体的行动与反思轨迹。"""

    def __init__(self):
        self.records: List[Dict[str, Any]] = []

    def add_record(self, record_type: str, content: str):
        """
        向记忆中添加一条新记录。
        record_type: 'execution' 或 'reflection'
        content: 生成的代码 或 反思的反馈
        """
        record = {"type": record_type, "content": content}
        self.records.append(record)
        print(f"📝 记忆已更新，新增一条 '{record_type}' 记录。")

    def get_trajectory(self) -> str:
        """获取完整的行动-反思轨迹文本。"""
        trajectory = []
        for record in self.records:
            trajectory.append(f"--- {record['type']} ---\n{record['content']}")
        return "\n\n".join(trajectory)

    def get_last_execution(self) -> Optional[str]:
        """获取最近一次的执行结果（初稿）。"""
        for record in reversed(self.records):
            if record["type"] == "execution":
                return record["content"]
        return None
```

### 3.3.4 Reflection 智能体的编码实现

```python
class ReflectionAgent:
    def __init__(self, llm_client, max_iterations=3):
        self.llm_client = llm_client
        self.memory = Memory()
        self.max_iterations = max_iterations

    def run(self, task: str) -> str:
        # --- ① 初始执行 ---
        print("🚀 开始执行...")
        initial_code = self._execute(task)
        self.memory.add_record("execution", initial_code)

        # --- ② 迭代反思与优化 ---
        for i in range(self.max_iterations):
            print(f"\n🔍 反思与优化，第 {i+1} 轮...")
            last_code = self.memory.get_last_execution()
            feedback = self._reflect(task, last_code)
            self.memory.add_record("reflection", feedback)

            # 若反馈表明已经很好，则提前结束
            if "无需改进" in feedback:
                print("✅ 已无需改进，提前结束迭代。")
                break

            refined_code = self._refine(task, last_code, feedback)
            self.memory.add_record("execution", refined_code)

        return self.memory.get_last_execution()

    def _execute(self, task: str) -> str:
        prompt = f"请完成任务，只输出最终结果：\n{task}"
        return self.llm_client.think(messages=[{"role": "user", "content": prompt}])

    def _reflect(self, task: str, code: str) -> str:
        prompt = f"""你是一个严格的结果评审员。请审视以下针对任务的解决方案，从事实性错误、逻辑漏洞、效率问题、遗漏信息四个维度给出反馈。
如果已经足够好，请直接回答"无需改进"。

任务：{task}
当前方案：
{code}
"""
        return self.llm_client.think(messages=[{"role": "user", "content": prompt}])

    def _refine(self, task: str, code: str, feedback: str) -> str:
        prompt = f"""你是一个结果优化专家。请根据反馈改进以下解决方案。

任务：{task}
原方案：
{code}
反馈：
{feedback}

请只输出改进后的完整方案。"""
        return self.llm_client.think(messages=[{"role": "user", "content": prompt}])
```

### 3.3.5 成本收益分析（第 4.4.5 节）

- **成本**：每轮"反思 + 优化"是额外的 LLM 调用 → Token 与延迟成倍增长。
- **收益**：答案质量显著提升，适合**对准确性和可靠性要求极高**的场景（代码生成、关键结论）。
- **结论**：**不是所有任务都值得 Reflection**——简单任务上它只是浪费钱。要评估"质量提升"是否值得"成本增加"。

## 3.4 三种范式怎么选（第 4.5 节，对应表 4.1）

| 范式 | 组织方式 | 核心优势 | 最适合 | 主要代价 |
|---|---|---|---|---|
| **ReAct** | 思考与行动**交织**在每一步 | 环境适应性、动态纠错 | 探索性任务、需要外部工具输入 | 步数多、上下文膨胀、解析脆弱 |
| **Plan-and-Solve** | 先规划、后执行，**两阶段解耦** | 结构性、稳定性、目标一致 | 逻辑路径确定的密集推理（数学、报告、代码结构） | 计划僵化、理解偏差被放大 |
| **Reflection** | 执行后**反复自评与修订** | 显著提升答案质量、可纠正策略级错误 | 高准确度要求（代码、关键结论） | 成本与延迟成倍增加 |

**组合使用（教材习题点明，实战常用）**：
- `Plan-and-Solve 规划 → 每步内部用 ReAct 执行`
- `ReAct 产出初稿 → Reflection 迭代优化`（本书第 4.4 节即此思路）
- `Reflection 的评审员本身可以用 Plan-and-Solve 的思维去查缺补漏`

## 3.5 必须掌握 / 易踩的坑

- ✅ 三个范式"思考-行动"的组织方式差异 + 选型场景。
- ✅ ReAct 的数学形式化（策略 π / 工具 T / 轨迹历史）。
- ✅ 工具三要素：名称 / 描述 / 执行逻辑（**描述最关键**）。
- ✅ 工具要"智能解析"，给 LLM 提供高质量输入。
- ✅ Plan-and-Solve 两阶段 + 状态管理（history 逐级传递）。
- ✅ Reflection 三步 + 记忆模块的必要性 + 成本收益权衡。
- ⚠️ 正则解析 LLM 输出是最大脆弱点——换模型/加换行就可能失效。
- ⚠️ 工具调用失败要有**纠正机制**（第 4 章习题：如何引导模型在多次调用错误工具后自我纠正？）。
- ⚠️ 忘记设置最大步数 = 死循环 + 烧钱。
- ⚠️ Reflection 别对简单任务用；迭代上限要设好，否则无限循环。
- ⚠️ Plan-and-Solve 的规划格式必须**严格可解析**（强制 `["步骤1", "步骤2"]`），否则执行器会崩。

## 3.6 一页速查（Q&A 自测）

1. ReAct 相比 CoT 多了什么？→ 与外部世界交互的 Action + Observation 循环。
2. ReAct 的三段轨迹？→ Thought（内心独白）、Action（具体动作）、Observation（工具返回）。
3. 工具三要素哪个最关键？→ 描述（LLM 靠它决定用哪个工具）。
4. 什么是工具的"智能解析"？→ 优先返回答案框/知识图谱等高质量直接答案。
5. Plan-and-Solve 的两个阶段？→ 规划（生成步骤计划）、执行（逐步求解）。
6. Plan-and-Solve 的规划输出格式为什么重要？→ 必须可被代码解析，否则执行阶段无法运行。
7. Reflection 的三步？→ 执行、反思、优化。
8. Reflection 为什么需要记忆模块？→ 迭代前提是能记住之前的尝试和反馈，且避免上下文冗余。
9. Reflection 的评审四维度？→ 事实性错误、逻辑漏洞、效率问题、遗漏信息。
10. 三种范式能组合吗？举例。→ 能，如"Plan-and-Solve 规划 + 每步 ReAct 执行"或"ReAct 出初稿 + Reflection 优化"。
11. ReAct 的主要工程风险？→ 正则解析脆弱 + 上下文膨胀 + 死循环。
12. 什么任务不值得用 Reflection？→ 简单任务（成本上升但收益有限）。
