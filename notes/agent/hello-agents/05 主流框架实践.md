## 5.1 从手动实现到框架开发（第 6.1 节）

这是从"**编写一次性脚本**"到"**使用成熟框架**"的思维跃迁。

### 5.1.1 为何需要智能体框架

框架把"主循环、状态管理、工具调用、日志记录"等**共有工作**抽象封装。四点价值：

1. **提升代码复用与开发效率**：提供通用 `Agent` 基类/执行器，封装好 Agent Loop。
2. **实现核心组件的解耦与可扩展性**：**模型层 Model Layer / 工具层 Tool Layer / 记忆层 Memory Layer** 分离——如滑动窗口、摘要记忆等策略可随意切换。
3. **标准化复杂的状态管理**：处理上下文窗口限制、历史持久化、多轮对话状态跟踪。
4. **简化可观测性与调试**：引入**事件回调机制**，在 `on_llm_start`、`on_tool_end`、`on_agent_finish` 等生命周期节点触发日志或上报。

### 5.1.2 主流框架的选型与对比

| 框架 | 核心抽象 | 一句话比喻 | 适合场景 |
|---|---|---|---|
| **AutoGen** | 可对话的智能体群聊 | 灵活的"**对话工作室**"——把多智能体协作简化为"圆桌会议" | 对话式协作、需要涌现式交互 |
| **AgentScope** | 消息驱动 + 组合式架构 | 完整的"**智能体操作系统**" | 大规模、高可靠性的生产级多智能体系统 |
| **CAMEL** | 角色扮演 + 引导性提示 | "**轻架构、重提示**"的极简双 Agent 协作 | 双 Agent 自主协作 |
| **LangGraph** | 状态机 + 有向图 | **显式控制的"流程图引擎"** | 需严格流程控制、循环/反思/自我修正 |

**各框架的定位**：
- **AutoGen**："通过对话实现协作"，把多智能体系统抽象为"可对话"智能体组成的群聊，可设定角色与交互规则（如 `Coder`/`ProductManager`/`Tester`）。
- **AgentScope**：专为多智能体应用设计的开发平台，核心特点是**易用性与工程化**，内置消息传递机制与分布式部署支持。
- **CAMEL**：**角色扮演（Role-Playing）**协作方法，在"**初始提示（Inception Prompting）**"引导下自主多轮对话。
- **LangGraph**：把执行流程建模为**图（Graph）**，节点（Node）= 每一步操作，边（Edge）= 跳转逻辑，**天然支持循环（Cycles）**。

## 5.2 框架一：AutoGen（第 6.2 节）

### 5.2.1 核心机制

分层设计：
- **`autogen-core`**：底层基础——与语言模型交互、消息传递。
- **`autogen-agentchat`**：构建于 core 之上，提供对话式智能体的高级接口。

**异步优先**：全面转向 `async/await`。

**两个核心组件**：
- **`AssistantAgent`**：任务主要解决者，封装 LLM，通过 System Message 赋予专家角色。
- **`UserProxyAgent`**：双重角色——人类用户代言人 + 可执行代码/调用工具的执行器。**"清晰地区分了'思考'与'行动'。"**

**协调机制**：从早期 `GroupChatManager` 演进为更灵活的 `Team`/群聊概念，如 `RoundRobinGroupChat`（轮询群聊）。

**轮询群聊工作流**：① 创建 `RoundRobinGroupChat` 并加入所有协作智能体 → ② 任务开始时按预设顺序依次激活 → ③ 被选中智能体根据当前对话上下文响应 → ④ 群聊把新回复加入历史并激活下一个 → ⑤ 持续到最大轮次或满足终止条件。
> "通过这种方式，AutoGen 将复杂的协作关系，简化为一个流程清晰、易于管理的自动化'**圆桌会议**'。"

### 5.2.2 案例：软件开发团队

- **目标**：构建"**实时显示比特币当前价格**"的 Web 应用。
- **四角色**：`ProductManager`（需求理解与分析）、`Engineer`（技术方案实施）、`CodeReviewer`（代码审查）、`UserProxy`（用户代言/执行）。
- 协作记录以 `TextMessage (角色)` 形式逐条打印，最终由 `UserProxy` 输入 `TERMINATE` 结束，输出"参与智能体数量：4 个 / 任务完成状态：成功"。

### 5.2.3 核心代码实现

```python
import os
import asyncio
from autogen_agentchat.agents import AssistantAgent, UserProxyAgent
from autogen_agentchat.teams import RoundRobinGroupChat
from autogen_ext.models.openai import OpenAIChatCompletionClient

# ① 创建模型客户端（可对接 OpenAI 官方、Azure OpenAI 及本地服务如 Ollama）
model_client = OpenAIChatCompletionClient(
    model=os.getenv("LLM_MODEL_ID", "gpt-4o"),
    api_key=os.getenv("LLM_API_KEY"),
    base_url=os.getenv("LLM_BASE_URL", "https://api.openai.com/v1"),
)

# ② 定义四个智能体（各自 System Message 赋予专家角色）
product_manager = AssistantAgent(
    name="ProductManager",
    model_client=model_client,
    system_message="你是产品经理，负责理解需求并拆解任务。",
)
engineer = AssistantAgent(
    name="Engineer", model_client=model_client,
    system_message="你是工程师，负责实现技术方案。",
)
code_reviewer = AssistantAgent(
    name="CodeReviewer", model_client=model_client,
    system_message="你是代码审查员，负责审查代码质量。",
)
user_proxy = UserProxyAgent(name="UserProxy")            # 用户代言 + 执行器

# ③ 组成轮询群聊
team = RoundRobinGroupChat(
    participants=[product_manager, engineer, code_reviewer, user_proxy],
    max_turns=20,
)

async def main():
    result = await team.run(task="开发一个能实时显示比特币价格的Web应用")
    print(f"参与智能体数量：{len(team.participants)}个")
    print(f"任务完成状态：{'成功' if result else '失败'}")

asyncio.run(main())
```

**非 OpenAI 模型需传 `model_info`**：

                "structured_output": True},

### 5.2.4 优势与局限性

- ✅ 对话式协作直观；多角色分工灵活；异步支持好。
- ⚠️ 基于 LLM 的对话本质具有不确定性，"智能体可能会产生偏离预期的回复，导致对话走向意外的分支，甚至陷入循环"。
- ⚠️ 结果不达预期时得到的是"**一长串的对话历史**"而不是错误堆栈——"**对话式调试**"的难题。

## 5.3 框架二：AgentScope（第 6.3 节）

### 5.3.1 设计

采用**组合式架构**与**消息驱动模式**。分层：
- **基础组件层**：`Message`、`Memory`、`Model API`、`Tool`。
- **智能体基础设施层**：预构建智能体（浏览器使用、深度研究）、ReAct 范式、智能体钩子、并行工具调用、状态管理、原生异步执行与实时控制。
- **多智能体协作层**：`MsgHub` 消息中心 + `Pipeline`（支持顺序/并发执行模式）。
- **开发与部署层**：`AgentScope Runtime` 生产级运行时 + `AgentScope Studio` 可视化开发工具链。

**消息驱动机制**（核心）：所有智能体交互抽象为**消息的发送与接收**，而非函数调用。
- 优势：**异步解耦、位置透明、可观测性、可靠性**（消息可持久化与重试）。
- 生命周期基于统一基类 `AgentBase`，开发者通常只需关注 `reply` 方法（另有可选 `observe`）。
- `MsgHub` 特点：灵活消息路由（点对点、广播、组播）、消息持久化（自动保存到 SQLite、MongoDB 等）、原生分布式支持（通过 RPC 自动处理跨节点通信，对开发者透明）。

```python
from agentscope.message import Msg
from agentscope.agents import AgentBase

msg = Msg(name="Alice", content="Hello, Bob!", role="user",
          metadata={"timestamp": ..., "message_type": "text", "priority": "normal"})

class MyAgent(AgentBase):
    def reply(self, x: Msg) -> Msg:
        # 实现对消息的响应逻辑
        return Msg(name=self.name, content="...", role="assistant")
    def observe(self, x: Msg) -> None:
        # 可选：观察不发言的消息
        ...
```

### 5.3.2 案例：三国狼人杀游戏

**三层设计**：
1. **游戏控制层**：`ThreeKingdomsWerewolfGame` 主控制器——维护全局状态、推进流程、裁定胜负。
2. **智能体交互层**：完全由 `MsgHub` 驱动。
3. **角色建模层**：每个玩家是基于 `DialogAgent` 的实例，注入"**游戏角色 + 三国人格**"双重身份。

**两个精妙设计**：
- **用消息驱动代替状态机**：狼人阶段通过 `MsgHub` 动态创建**仅含狼人玩家的私密频道**（`enable_auto_broadcast=True`）；投票阶段用 `fanout_pipeline(..., structured_model=WerewolfKillModelCN, enable_gather=False)` 并行收集决策。
- **用结构化输出约束游戏规则**：为不同行为定义 Pydantic 数据模型——
  - `DiscussionModelCN`：含 `reach_agreement`、`confidence_level`(1-10)、`key_evidence`；
  - `WitchActionModelCN`：含 `use_antidote`、`use_poison`、`target_name`。
  - 结果："女巫无法同时对同一目标使用解药和毒药""预言家每晚只能查验一名玩家"等规则**由字段定义与验证逻辑自动执行**。

### 5.3.3 优势与局限性

- ✅ 工程化程度高、原生分布式、消息持久化、可观测性强。
- ⚠️ 消息驱动架构对开发者技术要求较高（需理解异步编程、分布式通信）。
- ⚠️ 对简单多智能体对话场景"可能显得过于复杂，存在'**过度工程化**'的风险"；生态与社区资源仍待完善。
- 定位：更适合大规模、高可靠性的生产级系统。

## 5.4 框架三：CAMEL（第 6.4 节）

### 5.4.1 自主协作

**两大基石**：角色扮演 + 引导性提示。

**双智能体**：
- **"AI 用户"**：提需求、下达指令、构思步骤。
- **"AI 助理"**：执行操作、提供方案。
- 例：资深股票交易员 × 优秀的 Python 程序员。

**引导性提示（Inception Prompting）**：对话开始前注入的、结构化的初始指令（System Prompt），包含四部分：
1. 明确自身角色；
2. 告知协作者角色；
3. 定义共同目标；
4. 设定行为约束与沟通协议（要求"**一次只提出一个清晰、具体的步骤**"、规定用 `<SOLUTION>` 之类的标志标识完成）。

### 5.4.2 案例：AI 科普电子书

AI 心理学家与 AI 作者合作创作"拖延症心理学"短篇电子书。

```python
from camel.societies import RolePlaying
from camel.models import ModelFactory
from camel.types import ModelPlatformType

# 创建角色扮演会话（AI 用户 + AI 助理）
role_play_session = RolePlaying(
    assistant_role_name="心理学作者",
    user_role_name="心理学专家",
    task_prompt="合作撰写一篇关于拖延症心理学的短篇电子书",
    model=ModelFactory.create(model_platform_type=ModelPlatformType.OPENAI,
                              model_type="gpt-4o"),
)

# 初始化对话（得到 AI 生成的初始消息）
init_msg = role_play_session.init_chat()
for _ in range(10):
    assistant_response, user_response = role_play_session.step()
    print(assistant_response.msg.content)      # 迭代 assistant_response.msg
```

### 5.4.3 优势与局限性

- ✅ "**轻架构、重提示**"，实现极简、上手快。
- ⚠️ 成功很大程度取决于**初始提示质量** → 提示设计门槛、调试复杂（难以定位是角色定义、任务描述还是交互规则的问题）；不同 LLM 对相同提示的理解存在差异。
- ⚠️ 大规模多智能体场景下缺乏对话路由、分布式状态同步与冲突仲裁机制。
- 选型对照：**严格流程控制更适合 LangGraph、大规模并发更适合 AgentScope、复杂决策树更适合 AutoGen**。

## 5.5 框架四：LangGraph（第 6.5 节）

### 5.5.1 结构梳理

把执行流程建模为**状态机（State Machine）**并表示为**有向图**。三个基本要素：

| 要素 | 说明 |
|---|---|
| **全局状态（State）** | 通常用 Python `TypedDict` 定义，图内所有节点均可读写 |
| **节点（Node）** | 接收当前状态、返回更新后状态的 Python 函数 |
| **边（Edge）** | 定义跳转逻辑，含**条件边**实现动态路由 |

核心调用：`StateGraph(State)` → `add_node` / `add_edge` / `add_conditional_edges` → `compile()`。

> 革命性之处：**"这种设计的革命性之处在于它天然支持循环，使得构建能够进行迭代、反思和自我修正的复杂智能体工作流变得前所未有的直观和简单。"**

### 5.5.2 案例：三步问答助手

**固定三步流程**：理解（分析查询意图）→ 搜索（检索相关信息）→ 回答（基于意图与检索结果生成答案）。

```python
from typing import Annotated, TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages
from langgraph.checkpoint.memory import InMemorySaver
from langchain_openai import ChatOpenAI
from tavily import TavilyClient

# ① 定义全局状态
class SearchState(TypedDict):
    messages: Annotated[list, add_messages]
    user_query: str
    search_query: str
    search_results: str
    final_answer: str
    step: str

# ② 定义节点
def understand_query_node(state: SearchState) -> dict:
    """理解查询意图，并生成搜索关键词。"""
    llm = ChatOpenAI(model="gpt-4o")
    resp = llm.invoke([{"role": "user",
        "content": f"分析这个问题的意图并给出搜索关键词：{state['user_query']}"}])
    return {"search_query": resp.content, "step": "understood"}

def tavily_search_node(state: SearchState) -> dict:
    """用 Tavily 检索相关信息。"""
    try:
        client = TavilyClient()
        res = client.search(query=state["search_query"], max_results=3)
        results = "\n".join(f"- {r['title']}: {r['content']}" for r in res["results"])
        return {"search_results": results, "step": "searched"}
    except Exception as e:
        return {"search_results": "", "step": "search_failed"}

def generate_answer_node(state: SearchState) -> dict:
    """基于意图与检索结果生成答案；检索失败则用模型内部知识兜底。"""
    llm = ChatOpenAI(model="gpt-4o")
    if state.get("step") == "search_failed" or not state.get("search_results"):
        prompt = f"请用你的知识回答：{state['user_query']}（并告知用户未检索到实时信息）"
    else:
        prompt = f"根据以下资料回答：\n{state['search_results']}\n\n问题：{state['user_query']}"
    resp = llm.invoke([{"role": "user", "content": prompt}])
    return {"final_answer": resp.content, "step": "answered"}

# ③ 构建图
workflow = StateGraph(SearchState)
workflow.add_node("understand", understand_query_node)
workflow.add_node("search", tavily_search_node)
workflow.add_node("answer", generate_answer_node)

workflow.add_edge(START, "understand")
workflow.add_edge("understand", "search")
workflow.add_edge("search", "answer")
workflow.add_edge("answer", END)

# ④ 编译（带记忆检查点）
app = workflow.compile(checkpointer=InMemorySaver())

# 运行
result = app.invoke({"user_query": "北京有哪些值得去的景点？"},
                    config={"configurable": {"thread_id": "1"}})
print(result["final_answer"])
```

**条件边与循环**（LangGraph 的杀手锏）：定义 `should_continue(state) -> str` 之类的路由函数，用 `workflow.add_conditional_edges(...)` 实现"**反思-修正**"循环。

### 5.5.3 优势与局限性

- ✅ 流程可控、天然支持循环、状态显式、易于调试与持久化。
- ⚠️ 需更多前期**样板代码（Boilerplate）**——"开发者需要更多地思考'**如何控制流程（how）**'，而不仅仅是'做什么（what）'"。
- ⚠️ 缺少对话式智能体的"涌现"式交互。
- ⚠️ 调试需**全局理解**——问题可能来自节点内部逻辑错误、节点间状态数据异变，或边跳转条件判断失误。

## 5.6 框架选型的核心权衡（第 6.6 节）

> **"涌现式协作"（AutoGen / CAMEL：让智能体自由对话产生结果） vs "显式控制"（LangGraph：开发者精确编排每一步）。**

**简易判断表**：

| 需求 | 推荐 |
|---|---|
| 需要严格流程控制、循环/反思/自我修正 | **LangGraph** |
| 大规模、高可靠性的生产级多智能体系统 | **AgentScope** |
| 复杂决策树、对话式协作 | **AutoGen** |
| 双 Agent 自主协作、追求轻量快速上手 | **CAMEL** |

## 5.7 必须掌握 / 易踩的坑

- ✅ 框架的四点价值（复用、解耦、状态管理、可观测性）。
- ✅ 四个框架的核心抽象与"世界观"。
- ✅ 核心权衡：涌现式协作 vs 显式控制。
- ✅ AutoGen 的 `AssistantAgent` + `UserProxyAgent`（思考/行动分离）。
- ✅ AgentScope 的消息驱动 + 结构化输出约束规则。
- ✅ CAMEL 的引导性提示四要素。
- ✅ LangGraph 的状态 + 节点 + 边（+ 条件边/循环）。
- ⚠️ AutoGen 的"对话式调试"难题（看到的是一长串对话而非堆栈）。
- ⚠️ 对简单场景用 AgentScope / LangGraph 可能"过度工程化"。
- ⚠️ CAMEL 的成功高度依赖初始提示质量，调试困难。
- ⚠️ LangGraph 样板代码多，调试需全局理解。
- ⚠️ AutoGen 非 OpenAI 模型必须传 `model_info`。
