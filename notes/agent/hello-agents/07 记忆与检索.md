## 7.1 为什么需要记忆与检索（第 8.1 节）

### 7.1.1 认知科学启发

人类记忆的三层结构，直接对应工程组件：

| 人类记忆 | 持续时间/容量 | 对应组件 |
|---|---|---|
| **感觉记忆** | 0.5~3 秒，容量巨大 | 感知记忆（多模态） |
| **工作记忆** | 15~30 秒，容量 7±2 个项目 | `WorkingMemory`（TTL + 容量） |
| **长期记忆** | 可达终生、容量几乎无限 | 情景记忆 + 语义记忆 |
| ┗ 程序性记忆 | 技能与习惯 | —— |
| ┗ 陈述性记忆 | 可语言表达 | ┗ 语义记忆（一般知识/概念）+ 情景记忆（个人经历/事件） |

把认知阶段映射为技术操作：**编码（Encoding）→ 存储（Storage）→ 检索（Retrieval）→ 整合（Consolidation）→ 遗忘（Forgetting）**。

### 7.1.2 两个根本局限

**局限一：无状态导致的对话遗忘**

> **"当前的大语言模型虽然强大，但设计上是无状态的。"**

带来的四个问题：**上下文丢失、个性化缺失、学习能力受限、一致性问题**。

⚠️ **常见误解澄清**：第 7 章的 `SimpleAgent` 会在同一实例的 `_history` 中暂存当前对话，同一进程同一实例内的连续对话可携带最近上下文——但
> **"这种历史只是临时消息列表，不会跨会话持久化，也不能进行长期检索、遗忘和整合。"**

**局限二：内置知识的局限**
- **知识时效性**：训练数据有时间截止点。
- **专业领域知识**不足。
- **事实准确性**：通过检索验证可减少幻觉。
- **可解释性**：能提供信息来源。

**RAG 的核心思想**："在模型生成回答之前，先从一个外部知识库（如文档、数据库、API）中**检索**出最相关的信息，并将这些信息作为上下文一同提供给模型。"

### 7.1.3 记忆系统四层架构

```
基础设施层：MemoryManager（统一调度协调）· MemoryItem（标准化记忆项）
           · MemoryConfig（配置管理）· BaseMemory（记忆基类）
记忆类型层：WorkingMemory（临时信息+TTL）· EpisodicMemory（具体事件+时间序列）
           · SemanticMemory（抽象知识+图谱关系）· PerceptualMemory（多模态数据）
存储后端层：QdrantVectorStore · Neo4jGraphStore · SQLiteDocumentStore
嵌入服务层：DashScopeEmbedding（云端）· LocalTransformerEmbedding（离线）
           · TFIDFEmbedding（轻量兜底）
```

### 7.1.4 RAG 系统四层架构

```
文档处理层：DocumentProcessor · Document · Pipeline
嵌入表示层：统一嵌入接口（复用记忆系统的嵌入服务）
向量存储层：QdrantVectorStore（命名空间隔离）
智能问答层：多策略检索（向量检索 + MQE + HyDE）· 上下文构建（智能片段合并与截断）· LLM 增强生成
```

**重要原则**：**记忆与 RAG 被实现为两个独立工具**（延续"万物皆为工具"，而非创建新的 Agent 类）：
- `memory_tool`：存储和维护对话过程中的交互信息。
- `rag_tool`：从知识库检索相关信息作为上下文，**并可将重要的检索结果自动存储到记忆系统**。

## 7.2 记忆系统（第 8.2 节）

### 7.2.1 四类记忆的定位

| 类型 | 类比 | 存储 | 检索方式 | 用途 |
|---|---|---|---|---|
| **工作记忆** | 短期记忆 | **纯内存**（默认 50 条 + TTL 默认 60 分钟） | TF-IDF 词项权重 + 关键词匹配 | 当前会话的临时信息 |
| **情景记忆** | 个人经历 | **SQLite（结构化）+ Qdrant（向量）** | 结构化预过滤 + 向量语义检索 | 具体交互事件、学习经历，支持按时间/主题"复盘" |
| **语义记忆** | 知识体系 | **Neo4j（图）+ Qdrant（向量）** | 向量检索 + 图检索融合 | 抽象知识、用户偏好、需长期遵守的指令、领域知识点 |
| **感知记忆** | 多模态 | **模态分离的独立向量集合** | 按模态取对应向量库 + 跨模态对齐 | 图像、音频等（默认关闭） |

**四类记忆的详细说明**：
- **工作记忆**：默认 50 条、生命周期与单个会话绑定、会话结束自动清理。
- **情景记忆**：长期存储具体交互事件与学习经历，支持按时间序列或主题回顾式检索，是"**复盘**"和学习过往经验的基础。
- **语义记忆**：抽象知识、概念和规则（如用户偏好、需长期遵守的指令、领域知识点），"具有高度的持久性和重要性，是智能体形成'知识体系'和进行关联推理的核心"。
- **感知记忆**：图像、音频等多模态信息并支持跨模态检索。

### 7.2.2 检索评分公式（精华，背下来）

```python
# 工作记忆：(相关性 × 时间衰减) × (0.8 + 重要性 × 0.4)
# 情景记忆：(向量相似度 × 0.8 + 时间近因性 × 0.2) × (0.8 + 重要性 × 0.4)
# 语义记忆：(向量相似度 × 0.7 + 图相似度 × 0.3)   × (0.8 + 重要性 × 0.4)
# 感知记忆：(向量相似度 × 0.8 + 时间近因性 × 0.2) × (0.8 + 重要性 × 0.4)

# 时间近因性（指数衰减，模拟人类遗忘曲线）：
recency_score = math.exp(-decay_factor * age_hours / 24)   # decay_factor = 0.1
recency_score = max(0.1, recency_score)                    # 下限 0.1
```

**三个设计细节**：
- 重要性权重被刻意**限制在 [0.8, 1.2]**——目的是"**避免重要性过度影响相似度排序，保持检索的准确性**"。
- 语义记忆里向量权重 0.7（保证语义相关）> 图权重 0.3（关系推理补充）。
- ⚠️ 工作记忆用 TF-IDF，只做**词法相似度**——"TF-IDF 的向量化表示来自词频和逆文档频率，**并不等同于基于稠密嵌入的语义检索**"。

### 7.2.3 MemoryTool：统一入口、分发处理

**（1）add：四类记忆的添加**（`importance` 取值 0.0~1.0 —— "这个机制模拟了人类大脑对不同信息重要性的评估"）

**（3）forget：三种遗忘策略**


### 7.2.5 四种记忆类型的实现要点

**工作记忆（WorkingMemory）**
- 容量有限（默认 50 条）+ TTL 自动清理（默认 60 分钟）。
- **纯内存存储，访问速度极快，但系统重启后会丢失**——正符合其存储临时易变信息的定位。
- 检索：**组合词法检索**（TF-IDF 词项权重相似度 + 关键词匹配）。
- 评分公式：`(相关性 × 时间衰减) × (0.8 + 重要性 × 0.4)`。

**情景记忆（EpisodicMemory）**
- **SQLite + Qdrant 混合存储**——"SQLite 负责结构化数据的存储和复杂查询，Qdrant 负责高效的向量检索"。
- 添加时构造 `Episode(episode_id, session_id, timestamp, content, context)` 并维护 `sessions` 会话索引。
- 检索：结构化预过滤（时间范围、重要性）+ 向量语义检索（`limit × 5`）+ 综合评分排序。
- 评分公式：`(向量相似度 × 0.8 + 时间近因性 × 0.2) × (0.8 + 重要性 × 0.4)`，"确保检索结果既语义相关又时间相关"。

**语义记忆（SemanticMemory）**
- **Neo4j 图数据库 + Qdrant 向量库混合架构**。
- 添加：先嵌入 → `_extract_entities` / `_extract_relations` → 写入图库与向量库（metadata 含 `entities`、`entity_count`）。
- 检索：同时做 `_vector_search` 与 `_graph_search`，再 `_combine_and_rank_results`。
- 评分公式：`(向量相似度 × 0.7 + 图相似度 × 0.3) × (0.8 + 重要性 × 0.4)`。
- 用 HuggingFace 中文预训练模型做嵌入、加载 `zh_core_web_sm`/`en_core_web_sm` 做中英文处理。

**感知记忆（PerceptualMemory）**
- **模态分离的存储策略**——"为不同模态的数据创建独立的向量集合，这种设计避免了维度不匹配的问题"。
- 检索：按模态取对应向量库（`_get_vector_store_for_modality`），用 `where` 过滤 `memory_type`/`user_id`/`modality`，再按 `(向量相似度 × 0.8 + 时间近因性 × 0.2) × (0.8 + 重要性 × 0.4)` 融合排序。
- 支持通过统一向量空间实现跨模态语义对齐。

## 7.3 RAG 系统（第 8.3 节）

### 7.3.1 RAG 的构成与三阶段演进

RAG 可拆为三个动作：
- **检索（Retrieval）**：从知识库查询相关内容。
- **增强（Augmentation）**：将检索结果融入提示词辅助生成。
- **生成（Generation）**：输出兼具准确性与透明度的答案。

两个阶段：**数据准备阶段**（数据提取、文本分割、向量化）+ **应用阶段**（提问、检索、注入 Prompt、生成答案）。

| 阶段 | 时期 | 特征 |
|---|---|---|
| **朴素 RAG**（Naive） | 2020-2021 | "检索-读取"（Retrieve-Read），主要依赖 `TF-IDF` / `BM25` 等**关键词匹配**，检索结果不加处理直接拼接 |
| **高级 RAG**（Advanced） | 2022-2023 | 转向**稠密嵌入（Dense Embedding）**语义检索，引入查询重写、文档分块、重排序 |
| **模块化 RAG**（Modular） | 2023-至今 | 可插拔可组合模块：检索侧（混合检索、多查询扩展、假设性文档嵌入）+ 生成侧（思维链推理、自我反思与修正） |

### 7.3.2 工作机制与主流程

两个主要工作模式：**数据处理流程**（处理和存储知识文档）与**查询与生成流程**。

数据处理采取工具 **MarkItDown**——"设计思路是将传入的一切外部知识源统一转化为 Markdown 格式进行处理"。

```
任意格式文档 → MarkItDown 转换 → Markdown 文本 → 智能分块 → 向量化 → 存储检索
```

**多模态文档载入**：
- **MarkItDown**（微软开源的通用文档转换工具）为统一转换引擎，支持 PDF、Word、Excel、PowerPoint、图片（JPG/PNG/GIF，通过 OCR）、音频等。
- PDF 走 `_enhanced_pdf_processing` 增强处理；其余格式 `md_instance.convert(path)`；转换失败则回退 `_fallback_text_reader`。

### 7.3.3 智能分块策略（Markdown 结构感知）

```
标准Markdown文本 → 标题层次解析 → 段落语义分割 → Token计算分块
                → 重叠策略优化 → 向量化准备
```

**六层价值**：统一格式/结构清晰、`#/##/###` 层次识别、语义边界/完整性保证、大小控制/检索优化、信息连续性/上下文保持、嵌入向量/相似度匹配。

**实现要点**：
- `_split_paragraphs_with_headings`：依据标题层级维护 `heading_stack`，生成 `heading_path`（用 " > " 连接）与 `start`/`end` 字符位置。
- `_chunk_paragraphs(paragraphs, chunk_tokens, overlap_tokens)`：按 Token 数聚合段落，生成分块，并**用尾部段落回填 overlap**。
- `_approx_token_len`：中英文混合估算——"**CJK 字符按 1 token 计算**"，其他字符按空白分词计数（`_is_cjk` 覆盖 CJK 统一汉字及扩展 A-E、兼容汉字区间）。
- 示例参数：`chunk_size=1000, chunk_overlap=200`。

### 7.3.5 高级检索策略：MQE 与 HyDE（精华）

**多查询扩展（MQE, Multi-Query Expansion）**
- 用 LLM 生成**语义等价或互补的多样化查询**（如"如何学习 Python" → "Python 入门教程" / "Python 学习方法" / "Python 编程指南"）。
- 并行执行并合并结果，**提升召回率**。
- 实现函数 `_prompt_mqe(query, n)`，system prompt："你是检索查询扩展助手。生成语义等价或互补的多样化查询。使用中文，简短，避免标点。"
- **擅长解决"用词多样性"问题。**

**假设文档嵌入（HyDE, Hypothetical Document Embeddings）**
- 核心思想："**用答案找答案**"——先让 LLM 生成一个假设性的答案段落，再用它去检索真实文档。
- **缩小"问题（疑问句）"与"文档（陈述句）"之间的语义鸿沟。**
- 实现函数 `_prompt_hyde(query)`。
- 关键洞察："即使假设答案的内容不完全正确，它所包含的**关键术语、概念和表述风格**也能有效引导检索系统找到正确的文档。"
- **擅长解决"语义鸿沟"问题。**

**统一扩展检索框架（扩展-检索-合并三步）**

```python
search_vectors_expanded(
    store, query, top_k=8, rag_namespace=None, only_rag_data=True,
    score_threshold=None,
    enable_mqe=False, mqe_expansions=2,      # 多查询扩展
    enable_hyde=False,                        # 假设文档嵌入
    candidate_pool_multiplier=4,              # 候选池放大倍数
)
# 1) 生成扩展查询（MQE 多样化查询 + HyDE 假设文档）
# 2) 对每个扩展查询并行向量检索 → 候选文档池
#     候选池大小 pool = max(top_k * candidate_pool_multiplier, 20)
# 3) 去重 + 分数排序 → 返回 top-k
```

**选型建议（教材原话）**：
> "对于一般查询，建议启用 MQE；对于专业领域查询，建议同时启用 MQE 和 HyDE；对于性能敏感场景，可以只使用基础检索或仅启用 MQE。"
> "MQE 擅长处理用词多样性问题，HyDE 擅长处理语义鸿沟问题，而统一框架则确保了结果的质量和多样性。"
> 另提醒："在实际的使用场景里也需要去尝试寻找适合问题的解决方案。"

## 7.4 综合案例：智能文档问答助手（第 8.4 节）

以 Happy-LLM 公测 PDF（`Happy-LLM-0727.pdf`）为例，构建基于 **Gradio** 的 Web 应用（完整代码 `code/chapter8/11_Q&A_Assistant.py`）。核心类 `PDFLearningAssistant` **封装 `MemoryTool` 与 `RAGTool`**（而非直接调底层）。

**五个步骤形成完整闭环**：
1. 把 PDF 处理后的信息**记录到记忆系统**。
2. 检索结果也**记录到记忆系统**。
3. 展示记忆系统的完整功能（添加、检索、整合、遗忘）。
4. **整合 RAG 与 Memory 提供智能路由**。
5. 收集统计信息生成**学习报告**。

**`ask()` 的流程**（记忆 + 检索协同）：

```python
def ask(self, question):
    # ① 问题先写入工作记忆
    self.memory_tool.run("add", content=question, memory_type="working", importance=0.6)
    # ② RAG 检索并生成回答（可开启高级检索）
    answer = self.rag_tool.execute("ask", question=question, limit=5,
                                   enable_advanced_search=True,
                                   enable_mqe=True, enable_hyde=True)
    # ③ 问答对写入情景记忆（便于日后复盘）
    self.memory_tool.run("add", content=f"Q: {question}\nA: {answer}",
                         memory_type="episodic", importance=0.7,
                         event_type="qa_interaction")
    return answer
```

其他功能：`add_note`（笔记存入语义记忆）、`recall`、`get_stats`、`generate_report`（生成 JSON 报告）。
分块参数示例 `chunk_size=1000, chunk_overlap=200`；运行后访问 `http://localhost:7860`。

## 7.6 必须掌握 / 易踩的坑

- ✅ 记忆四大类型 + 各自存储后端 + 检索评分公式。
- ✅ 认知阶段五映射：编码/存储/检索/整合/遗忘。
- ✅ 三种遗忘策略 + consolidate（工作→情景→语义）。
- ✅ RAG 三阶段演进 + "转 Markdown → 结构感知分块 → 向量化"主流程。
- ✅ MQE（召回/用词多样性）与 HyDE（语义鸿沟）各自定位 + 统一扩展框架三步。
- ✅ 时间近因性用指数衰减模拟遗忘曲线。
- ⚠️ `_history` ≠ 记忆：不跨会话、无检索/遗忘/整合。
- ⚠️ TF-IDF 只是词法相似度，不等于稠密语义检索（工作记忆是轻量兜底）。
- ⚠️ 感知记忆默认关闭，避免不必要的资源消耗。
- ⚠️ 向量维度必须与嵌入模型匹配（`QDRANT_VECTOR_SIZE=384` 对应 MiniLM）；感知记忆按模态分离正是为避免维度不匹配。
- ⚠️ MQE/HyDE 都是额外 LLM 调用 → 成本增加，性能敏感场景不要全开。
- ⚠️ 重要性权重范围 [0.8, 1.2] 是刻意限制，别随意放大。

## 7.7 一页速查（Q&A 自测）

1. LLM 的两个根本局限？→ 无状态（记不住）+ 知识有限/过时（不知道）。
2. RAG 的核心思想？→ 生成前先检索相关信息作为上下文。
3. 四类记忆分别用什么存储？→ 工作=纯内存；情景=SQLite+Qdrant；语义=Neo4j+Qdrant；感知=模态分离向量库。
4. 检索评分里重要性权重范围与原因？→ [0.8, 1.2]，避免重要性过度影响相似度排序。
5. 工作记忆为什么不算"语义检索"？→ 用 TF-IDF 词法相似度。
6. MQE 与 HyDE 分别解决什么？→ 用词多样性 / 语义鸿沟。
7. consolidate 做什么？→ 把短期记忆（工作）转化为长期记忆（情景/语义）。
8. 为什么要统一转 Markdown？→ 统一格式、结构清晰、便于按标题层次分块。
9. 三种遗忘策略？→ 基于重要性、基于时间、基于容量。
10. 感知记忆为什么模态分离？→ 避免不同模态向量维度不匹配。
11. 记忆与 RAG 在框架中的形态？→ 都是 Tool（MemoryTool / RAGTool），不是新的 Agent 类。
