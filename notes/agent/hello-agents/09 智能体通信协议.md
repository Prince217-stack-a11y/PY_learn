# 09 智能体通信协议

> **教材**：第 10 章《智能体通信协议》
> **源码**：`code/chapter10/`（含 `weather-mcp-server` 自定义 MCP Server）
> **一句话**：智能体做大了就要"能接外部工具（**MCP**）""能彼此协作（**A2A**）""能在网络里被发现（**ANP**）"——三种协议共同构成**智能体通信的基础设施层**。

---

## 9.1 通信协议基础（第 10.1 节）

### 9.1.1 为什么需要协议

单体智能体的三个根本限制：
1. **工具集成困境**：每接一个服务都要写专门的 Tool 类，重复劳动。
2. **能力扩展瓶颈**：能力被限制在预定义工具集内。
3. **协作的缺失**：多智能体只能手动编排。

### 9.1.2 三种协议的定位（必背）

| 协议 | 提出方 | 解决的问题 | 设计哲学 | 成熟度 |
|---|---|---|---|---|
| **MCP** | Anthropic | 智能体 ↔ **外部工具/资源**的标准化通信 | **上下文共享**（"不仅仅是一个 RPC 协议"） | 生态相对成熟 |
| **A2A** | Google | **智能体 ↔ 智能体**的点对点通信 | **对等通信**（每个 Agent 既提供服务也消费服务，避免中心化协调器瓶颈） | 多为 Sample Code |
| **ANP** | 开源社区 | **大规模网络**中发现与连接智能体 | **去中心化服务发现** | 概念性框架，尚无成熟生态 |

**选型建议**：需要访问外部服务 → **MCP**；多个智能体协作 → **A2A**；构建大规模生态 → **ANP**。
第 10.6 节补充：**小规模协作推荐 A2A，大规模网络采用 ANP**。

> ⚠️ 教材提醒："协议目前发展处于早期，所以**无需花费太多精力去造轮子**。"
> **"优先利用成熟的社区 MCP 服务，以减少不必要的重复开发。"**

### 9.1.3 框架的协议架构（三层）

```
协议实现层：MCP（基于 FastMCP） / A2A（基于 Google 官方 a2a-sdk） / ANP（自研轻量模拟）
    ↑
工具封装层：MCPTool / A2ATool / ANPTool（都继承 BaseTool，提供一致的 run()）
    ↑
智能体集成层：所有智能体通过 Tool System 使用协议工具，无需关心底层细节
```

> 又是"**万物皆为工具**"：`agent.add_tool(MCPTool(...))` / `A2ATool(...)` / `ANPTool(...)`。

```bash
pip install "hello-agents[protocol]==0.2.2"
# 使用 npx 启动社区 MCP 服务器还需安装 Node.js（见 Additional-Chapter 文档）
```

## 9.2 MCP 协议实战（第 10.2 节）

### 9.2.1 架构与三大核心能力

**三层架构：Host — Client — Server**
- **Host（宿主层）**：用户直接交互的界面，管理对话流程。
- **Client（客户端层）**：与合适的 Server 建立连接、发送请求接收响应。
- **Server（服务器层）**：执行实际功能。
- 优势是**关注点分离**——"**开发者只需专注于开发对应的 MCP Server**"。

**完整交互流程**：用户问题 → Host → 模型分析 → 需要文件信息 → MCP Client 连接 → 文件系统 MCP Server → 执行操作 → 返回结果 → 模型生成回答 → 显示。

**三大核心能力（一定要区分清楚）**：

| 能力 | 主动性 | 含义 |
|---|---|---|
| **Tools** | **主动的** | 执行操作 |
| **Resources** | **被动的** | 提供数据 |
| **Prompts** | **指导性的** | 提供模板 |

**工具选择五步流程**：
① **工具发现**（Client 调用 `list_tools()` 获取名称、功能说明、参数定义）→ ② **上下文构建**（转换为 LLM 可理解格式加入系统提示词）→ ③ **模型推理**（决定是否调用、调用哪个）→ ④ **工具执行** → ⑤ **结果整合**。
> **"这个过程是完全自动化的……因此，编写清晰、准确的工具描述至关重要。"**

**MCP 与 Function Calling 的关系（面试高频）**：
- 二者**并非竞争，而是相辅相成**：**Function Calling 是模型内在能力**（决定何时调用、生成参数）；**MCP 是工程层面的基础设施协议**（标准化描述与调用工具）。
- 类比：**"Function Calling 相当于你学会了'如何打电话'……而 MCP 则是那个全球统一的'电话通信标准'。"**
- Function Calling 的痛点：不同 LLM 平台实现差异巨大（如 OpenAI 用 `parameters`、Claude 用 `input_schema`），**切换模型需重写代码**——MCP 解决了这个问题。

### 9.2.2 客户端基本操作

```python
from hello_agents.protocols import MCPClient

client = MCPClient(["npx", "-y", "@modelcontextprotocol/server-filesystem", "."])
async with client:
    tools = await client.list_tools()                       # 工具发现
    result = await client.call_tool("read_file", {"path": "a.txt"})   # 参数符合 JSON Schema
    resources = await client.list_resources()
    content = await client.read_resource(uri)
    prompts = await client.list_prompts()
    prompt = await client.get_prompt("summarize", {"text": "..."})
```
> GitHub MCP 需设置环境变量 `GITHUB_PERSONAL_ACCESS_TOKEN`（Windows：`$env:...`）。
> 调用工具建议用 try-except 包裹（更安全的 `safe_tool_call` 示例）。

### 9.2.3 传输层无关性（五种传输方式）

| 传输方式 | 用途 |
|---|---|
| **Memory** | 内存传输，用于测试/原型 |
| **Stdio** | 本地开发 |
| **Stdio with Args** | 带参数的本地启动 |
| **Stdio + npx** | 启动社区 MCP 服务器 |
| **HTTP / SSE / StreamableHTTP** | 远程传输 |

> ⚠️ **`MCPTool` 主要用于 Stdio 和 Memory 传输；HTTP/SSE 等远程传输建议直接使用底层 `MCPClient`。**

### 9.2.4 自动展开机制（很重要）

`MCPTool` 把 MCP 服务器提供的所有工具**展开为独立工具**并注册进 Agent 工具注册表（如内置计算器展开为 `calculator_add/subtract/multiply/divide/greet/get_system_info` 六个）。
- 包装器会按参数定义**自动做类型转换**（Agent 生成字符串 `a=25,b=16` → 转换为数字 `{"a":25.0,"b":16.0}`）。
- 调用时 Agent 输出 `[TOOL_CALL:calculator_multiply:a=25,b=16]`，包装器转成 `{"action":"call_tool","tool_name":"...","arguments":{...}}`。

> ⚠️ **多个 MCP 服务器必须指定不同的 `name`**，该 name 会作为展开工具名的前缀避免冲突（如 `name="fs"` → `fs_read_file`）。

### 9.2.5 MCP 社区生态（三个资源库）

- **Awesome MCP Servers**：社区精选列表。
- **MCP Servers Website**：官方目录站。
- **Official MCP Servers**：Anthropic 官方维护，**质量最高、文档最完善**。

案例：Playwright 自动化网页测试、Obsidian + Perplexity 智能笔记、Jira + GitHub 项目管理、YouTube + Notion + Spotify 内容创作。

## 9.3 A2A 协议实战（第 10.3 节）

### 9.3.1 定位与通信模型

**解决的问题**：智能体之间的协作——通信、委托任务、协商能力、同步状态。

**拓扑**：中央协调器（星型拓扑）存在**单点故障、性能瓶颈、扩展困难** → A2A 采用**点对点（P2P）/ 网状拓扑**。

**核心抽象**：**任务（Task）** 和 **工件（Artifact）**——"**这是它与 MCP 最大的区别**"。任务有标准化生命周期（创建、协商、代理、执行中、完成、失败等状态）。

**请求生命周期四步**：**代理发现 → 身份验证 → 发送消息 API → 发送消息流 API**。

### 9.3.2 最小用法

```python
from hello_agents.protocols import A2AServer, A2AClient

# 服务端：用装饰器定义技能
researcher = A2AServer(name="researcher", description="负责搜索和分析资料的Agent",
                       version="1.0.0")

@researcher.skill("research")
def handle_research(text: str) -> str:
    ...

# 客户端：调用技能
client = A2AClient("http://localhost:5000")
response = client.execute_skill("research", "research AI在医疗领域的应用")
```

**多 Agent 协作**：分别 `run(port=5000/5001/5002)`（后台线程启动），构成"**研究 → 撰写 → 编辑**"流程。
**接入 Agent**：`A2ATool(name=..., description=..., agent_url="http://localhost:5000")` 后 `coordinator.add_tool(researcher_tool)`。
**Agent 间协商**：`propose` / `negotiate` 技能返回 `accepted` / `counter_proposal`。

> ⚠️ 教材说明："**A2A 现有实现大部分为 `Sample Code`**，并且即使有 Python 的实现也较为繁琐，因此这里我们只采用**模拟协议思想**的方式。"

## 9.4 ANP 协议实战（第 10.4 节）

### 9.4.1 目标与核心机制

**目标**：**服务发现**（如何快速找到能处理任务的智能体）、**智能路由**（按负载/成本选择）、**动态扩展**。

**三步流程**：
1. **服务的发现与匹配**：通过公开发现服务基于语义/功能描述查询；发现服务预先爬取各智能体暴露的标准端点 `/.well-known/agent-descriptions` 建立索引。
2. **基于 DID 的身份验证**：智能体 A 用**私钥**对含自身 **DID** 的请求签名 → 智能体 B 解析 DID 获取**公钥**验证签名真实性与请求完整性。
3. **标准化的服务执行**：按预定义标准接口与数据格式交换。

> "该机制的核心是利用 **DID** 构建了一个**去中心化的信任根基**，并借助标准化的描述协议实现了服务的**动态发现**。"

### 9.4.2 用法

```python
discovery = ANPDiscovery()                       # 建服务发现中心
register_service(discovery, ...)                 # 注册服务
discover_service(discovery, service_type="nlp")  # 发现 → 或在返回列表里选负载最低者

network = ANPNetwork(network_id=...)
network.add_node(...)                            # 加节点 + 按能力匹配建连接
```
第 10.4.3 节演示了分布式任务调度与负载均衡函数。

## 9.5 构建自定义 MCP 服务器（第 10.5 节）

### 9.5.1 动机

封装业务逻辑、访问私有数据、性能专项优化、功能定制扩展（如集成专有算法或硬件设备）。

### 9.5.2 实现（用 `MCPServer` 写一个天气服务器）

```python
import json
from hello_agents.protocols import MCPServer

weather_server = MCPServer(name="weather-server", description="真实天气查询服务")

def get_weather(city: str) -> str:
    """获取指定城市的当前天气"""        # docstring 会成为工具描述！
    try:
        return json.dumps(get_weather_data(city), ensure_ascii=False, indent=2)
    except Exception as e:
        return json.dumps({"error": str(e), "city": city}, ensure_ascii=False)

def list_supported_cities() -> str:
    """列出支持查询的城市"""
    ...

weather_server.add_tool(get_weather)
weather_server.add_tool(list_supported_cities)
weather_server.add_tool(get_server_info)

if __name__ == "__main__":
    weather_server.run()               # stdio 启动
```

### 9.5.3 测试与在 Agent 中使用

```python
# 直接用 MCPClient 测试
client = MCPClient(["python", server_script])

    assistant.add_tool(expanded_tool)
```

## 9.6 统一抽象与实战经验（第 10.6 节）

- 所有协议都被**统一抽象为 Tool**：`agent.add_tool(MCPTool(...))` / `A2ATool(...)` / `ANPTool(...)`。
- **优先利用成熟的社区 MCP 服务，以减少不必要的重复开发。**
- **根据系统规模选择合适的协议：小规模协作场景推荐使用 A2A，大规模网络场景则应采用 ANP。**

## 9.7 必须掌握 / 易踩的坑

- ✅ 三协议定位：MCP=连工具、A2A=Agent 协作、ANP=大规模发现。
- ✅ MCP 的 Host/Client/Server 三层 + Tools/Resources/Prompts 三能力。
- ✅ MCP vs Function Calling 的关系（协议 vs 模型能力）。
- ✅ MCP 工具选择五步流程 + 自动展开机制。
- ✅ A2A 的 Task/Artifact 抽象 + P2P 拓扑。
- ✅ ANP 的三步流程（服务发现 / DID 验证 / 标准执行）。
- ✅ 写自定义 MCP Server 并发布到 Smithery。
- ⚠️ 多个 MCP 服务器必须用不同 `name`（作为展开工具名前缀）。
- ⚠️ `MCPTool` 主要用于 Stdio/Memory；远程传输建议直接用 `MCPClient`。
- ⚠️ 协议发展处于早期，A2A/ANP 的实现多为 Sample/概念模拟，别投入过多造轮子。
- ⚠️ Smithery 发布需要 `pyproject.toml` 与 `smithery.yaml`，Docker 端口 8081。
