## 1.1 什么是智能体

**定义**：任何能够通过**传感器（Sensors）**感知其所处**环境（Environment）**，并**自主**地通过**执行器（Actuators）**采取**行动（Action）**以达成特定目标的实体。

四个基本要素：
- **环境**：智能体所处的外部世界。自动驾驶汽车的环境是动态道路交通；交易算法的环境是金融市场。
- **传感器**：感知环境状态。摄像头、麦克风、雷达，或各类 **API 返回的数据流**。
- **执行器**：对环境施加影响。物理设备（机械臂、方向盘）或虚拟工具（执行代码、调用服务）。
- **自主性（Autonomy）**：**真正赋予智能体"智能"的部分**。它不是被动响应刺激或严格执行预设指令的程序，而是能基于感知与内部状态**独立决策**。感知→行动的闭环构成所有智能体行为的基础。

### 1.1.1 传统视角下的六类智能体（演进路线）

| 类型 | 核心机制 | 要回答的问题 | 典型例子 | 局限 |
|---|---|---|---|---|
| **简单反射智能体** | 工程师设计的"条件-动作"规则 | —— | 恒温器（室温高于设定值→启动制冷） | 无记忆、无预测，无法应对需理解上下文的复杂任务 |
| **基于模型的反射智能体** | 内部**世界模型（World Model）**追踪无法直接感知的环境方面 | "世界现在是什么样子的？" | 隧道中行驶的自动驾驶（保持对前车的存在/速度/位置的判断） | 只有初级"记忆"，仍是被动反应 |
| **基于目标的智能体** | 主动、有预见性地选择能导向特定未来状态的行动 | "我应该做什么才能达成目标？" | GPS 导航 | 目标单一，不做多目标权衡 |
| **基于效用的智能体** | 在多个目标间做权衡与优化 | "哪个行动带来的效用最高？" | 投资决策 | 效用函数难设计 |
| **学习型智能体** | 从经验中改进自身策略 | —— | AlphaGo | 样本效率低 |
| **混合式智能体** | 融合反应性与规划性 | —— | **LLM 智能体** | —— |

### 1.1.2 三个分类维度

**（1）按其智能水平/复杂度**：简单反射 → 基于模型的反射 → 基于目标 → 基于效用（见上表）。

**（2）按反应性 vs 规划性**：
- **反应式智能体（Reactive）**：对环境刺激近乎即时响应，决策延迟极低；遵循"感知→行动"直接映射，不做或极少规划。
  - 优势：**速度快、计算开销低**（安全气囊必须在碰撞的毫秒内反应；高频交易靠反应式决策捕捉机会）。
  - 代价："**短视**"——缺乏长远规划，容易陷入局部最优。
- **规划式智能体（Deliberative / 审议式）**：行动前先用内部世界模型系统探索未来各种可能性，评估不同行动序列的后果，找最优路径。
  - 类比：**棋手**——不只眼前一步，而是预想对手应对、规划后续十几步。
  - 优势：**战略性、有远见**（制定商业计划、规划长途旅行）。
  - 代价：**时间与计算成本高**，环境瞬息万变时可能错过最佳行动时机。
- **混合式智能体（Hybrid）**：
  - 经典架构是**分层设计**：底层快速反应模块处理紧急情况，高层审慎规划模块制定长远目标。
  - **现代 LLM 智能体是更灵活的混合模式**，在"思考-行动-观察"循环中融合两者：
    - **规划（Reasoning）**：在"思考"阶段分析状况、规划下一步——审议过程。
    - **反应（Acting & Observing）**：在"行动"和"观察"阶段与工具/环境交互并立即获得反馈——反应过程。
  - 效果：把一个需要长远规划的宏大任务，**分解为一系列"规划-反应"的微循环**，既灵活应对即时变化，又能连贯完成长期目标。

**（3）按知识表示**（一场持续半个多世纪的辩论，塑造了两种截然不同的 AI 文化）：
- **亚符号主义 AI（Sub-symbolic / 连接主义）**：知识不是显式规则，而是**内隐地分布在大量神经元组成的复杂网络中**，是从海量数据中学到的统计模式。
  - 类比：牙牙学语的孩童——不是学"猫有四条腿、毛茸茸、会喵喵叫"，而是看过成千上万张猫图后辨识出"猫"的视觉模式。
  - 优势：模式识别强、对噪声数据鲁棒，能处理图像/声音等非结构化数据。
  - 劣势：**黑箱（Black Box）**——能以惊人准确率识别猫，但无法解释"为什么"；纯逻辑推理任务表现不佳，易产生看似合理却事实错误的幻觉。
- **符号主义 AI（Symbolic）**：智能源于**对符号的逻辑操作**。符号是人类可读的实体（词语、概念），操作遵循严格逻辑规则。
  - 类比：一丝不苟的图书管理员——把世界知识整理为清晰的规则库与知识图谱。
  - 优势：**透明、可解释**，推理步骤可完整追溯（金融、医疗等高风险领域至关重要）。
  - 劣势：**脆弱**——依赖完备规则体系，现实中任何未被覆盖的新情况都可能导致系统失灵（"**知识获取瓶颈**"）。
- **神经符号主义 AI（Neuro-Symbolic）**："大和解"思想，目标是融合二者优点——既能像神经网络一样从数据中学习，又能像符号系统一样进行逻辑推理。
  - **绝佳类比：卡尼曼《思考，快与慢》的双系统理论**：
    - **系统 1**：快速、凭直觉、并行 → 亚符号主义强大的模式识别能力。
    - **系统 2**：缓慢、有条理、基于逻辑 → 符号主义的推理过程。
    - **神经符号主义**：让系统 1 与系统 2 协同工作。
  - **LLM 智能体是神经符号主义的极佳实践范例**：内核是巨大的神经网络（模式识别与语言生成）；工作过程中又生成一系列结构化中间步骤（**思想、计划、API 调用**），这些都是明确的、可操作的**符号**。

## 1.2 智能体的构成与运行原理

### 1.2.1 任务环境定义：PEAS 模型

用 **PEAS** 精确描述任务环境：**P**erformance（性能度量）、**E**nvironment（环境）、**A**ctuators（执行器）、**S**ensors（传感器）。

以**智能旅行助手**为例（教材表 1.2）：

| 维度 | 内容 |
|---|---|
| **性能度量 P** | 行程合理、预算可控、用户满意度、响应速度 |
| **环境 E** | 航班/酒店/景点 API、实时天气、用户需求、部分可观察的外网数据 |
| **执行器 A** | 调用工具（天气/景点/订票 API）、输出行程方案 |
| **传感器 S** | 用户输入、各类 API 返回值 |

**LLM 智能体数字环境的三个特性**（直接影响设计）：
1. **部分可观察**：旅行助手查航班时无法一次性获取所有航司全部实时座位信息，只能看到 API 返回的部分数据 → 需要**记忆**（记住已查询过的航线）+ **探索**（尝试其他接口）。
2. **动态性与随机性**：外部数据持续变化 → 不能写死规则，要动态推理。
3. **多目标**：既要准确、又要快、又要便宜 → 需要权衡。

### 1.2.2 核心机制：Agent Loop（全书最重要的图）

```
        ┌──────────────────────────────────────────────────┐
        │                                                  │
   感知 Perception ──→ 思考 Thought ──→ 行动 Action ──→ 环境状态变化
   (Observation)      ├─ 规划 Planning   (调用工具)      (State Change)
                      └─ 工具选择                            ↓
        ↑                                                  │
        └────────── 新的 Observation ←──────────────────────┘
```

**三个相互关联的阶段**：
1. **感知（Perception）**：循环起点。通过传感器（API 监听端口、用户输入接口）接收来自环境的输入信息，即**观察（Observation）**——可以是用户初始指令，也可以是上一步行动导致的状态变化反馈。
2. **思考（Thought）**：核心决策阶段（对 LLM 智能体即大模型驱动的内部推理），内部再分两个环节：
   - **规划（Planning）**：基于当前观察与内部记忆，更新对任务和环境的理解，制定或调整行动计划；可能涉及把复杂目标分解为更具体的子任务。
   - **工具选择（Tool Selection）**：从可用工具库中选择最适合执行下一步骤的工具，并确定调用所需的具体参数。
3. **行动（Action）**：通过执行器执行具体行动（如调用代码解释器、搜索引擎 API），对环境施加影响，意图改变环境状态。

**行动不是终点**：行动引起**环境状态变化**，环境随即产生**新的观察**作为结果反馈，又被感知系统捕获——形成持续的"**感知-思考-行动-观察**"闭环。智能体正是通过不断重复这个循环，从初始状态向目标状态演进。

### 1.2.3 智能体的感知与行动：交互协议

工程实践中，为了让 LLM 有效驱动循环，需要明确的**交互协议（Interaction Protocol）**规范信息交换。现代框架中这体现为对智能体**每一次输出的结构化定义**——输出不再是单一自然语言回复，而是遵循特定格式的文本，明确展示内部推理过程与最终决策。

**两个核心部分**：
- **Thought（思考）**：内部决策的"快照"——以自然语言阐述如何分析情境、回顾上一步观察、自我反思与问题分解，并规划下一步行动。
- **Action（行动）**：基于思考决定施加的具体操作，通常以**函数调用**形式表示。

```bash
Thought: 用户想知道北京的天气。我需要调用天气查询工具。
Action: get_weather("北京")
```

- 这里的 `Action` 字段构成**对外部世界的指令**，由外部**解析器（Parser）**捕捉并调用相应函数。
- 行动执行后环境返回结果（如 `get_weather` 返回 JSON）。但原始机器可读数据通常含 LLM 无需关注的冗余信息，且格式不符合其自然语言处理习惯。
- 因此**感知系统的一个重要职责是扮演传感器**：把原始输出处理封装为**简洁、清晰的自然语言文本**（即 Observation）。

## 1.3 动手：5 分钟实现第一个智能体

**任务定义**："你好，请帮我查询一下今天北京的天气，然后根据天气推荐一个合适的旅游景点。"
要完成它，智能体必须展现清晰的逻辑规划：先调天气工具，把观察结果作为下一步依据，再调景点推荐工具得出最终建议。

### 1.3.1 准备工作

```bash
pip install requests tavily-python openai
```

- `requests`：Python 社区最流行、最易用的 HTTP 库，用于访问网络 API。
- `tavily-python`：强大的 AI 搜索 API 客户端，用于获取实时网络搜索结果（[官网](https://www.tavily.com/) 注册获取 Key）。
- `openai`：OpenAI 官方 SDK，用于调用 GPT 等 LLM 服务。

### 1.3.2 指令模板（System Prompt）——智能体的"说明书"

驱动真实 LLM 的关键在于**提示工程**。我们要设计一个"指令模板"，告诉 LLM 应扮演什么角色、拥有哪些工具、如何格式化思考与行动。它将作为 `system_prompt` 传给 LLM：

```
AGENT_SYSTEM_PROMPT = """
你是一个智能旅行助手。你的任务是分析用户的请求，并使用可用工具一步步地解决问题。

# 可用工具:
- `get_weather(city: str)`: 查询指定城市的实时天气。
- `get_attraction(city: str, weather: str)`: 根据城市和天气搜索推荐的旅游景点。

# 输出格式要求:
你的每次回复必须严格遵循以下格式，包含一对Thought和Action：

Thought: [你的思考过程和下一步计划]
Action: [你要执行的具体行动]

Action的格式必须是以下之一：
1. 调用工具：function_name(arg_name="arg_value")
2. 结束任务：Finish[最终答案]

# 重要提示:
- 每次只输出一对Thought-Action
- Action必须在同一行，不要换行
- 当收集到足够信息可以回答用户问题时，必须使用 Action: Finish[最终答案] 格式结束

请开始吧！
"""
```

> **模板四要素（背下来）**：① 角色 ② 可用工具清单 ③ 严格输出格式（含结束标记） ④ 重要约束。这是所有 Agent 提示词的基本骨架。

### 1.3.3 工具 1：查询真实天气（wttr.in）

```python
import requests

def get_weather(city: str) -> str:
    """
    通过调用 wttr.in API 查询真实的天气信息。
    """
    # API端点，我们请求JSON格式的数据
    url = f"https://wttr.in/{city}?format=j1"
    try:
        response = requests.get(url)
        response.raise_for_status()          # 检查状态码是否为 200
        data = response.json()               # 解析 JSON
        current_condition = data['current_condition'][0]
        weather_desc = current_condition['weatherDesc'][0]['value']
        temp_c = current_condition['temp_C']
        return f"{city}当前天气：{weather_desc}，气温{temp_c}摄氏度"
    except requests.exceptions.RequestException as e:
        return f"错误：查询天气时遇到网络问题 - {e}"
    except (KeyError, IndexError) as e:
        return f"错误：解析天气数据失败，可能是城市名称无效 - {e}"
```

> **关键设计**：工具**永不抛异常**，所有错误都转成"错误：xxx"字符串返回。因为这些字符串会作为 Observation 回到 LLM，让它有机会自我纠正。

### 1.3.4 工具 2：搜索并推荐旅游景点（Tavily）

```python
import os
from tavily import TavilyClient

def get_attraction(city: str, weather: str) -> str:
    """
    根据城市和天气，使用Tavily Search API搜索并返回优化后的景点推荐。
    """
    api_key = os.environ.get("TAVILY_API_KEY")
    if not api_key:
        return "错误：未配置TAVILY_API_KEY环境变量。"

    tavily = TavilyClient(api_key=api_key)
    query = f"'{city}' 在'{weather}'天气下最值得去的旅游景点推荐及理由"
    try:
        response = tavily.search(query=query, search_depth="basic", include_answer=True)
        if response.get("answer"):
            return response["answer"]
        formatted = [
            f"- {r['title']}: {r['content']}"
            for r in response.get("results", [])[:3]
        ]
        return "根据搜索，为您找到以下景点:\n" + "\n".join(formatted)
    except Exception as e:
        return f"错误：执行Tavily搜索时出现问题 - {e}"
```

### 1.3.5 接入 LLM：兼容 OpenAI 接口的客户端

```python
from openai import OpenAI

class OpenAICompatibleClient:
    """一个用于调用任何兼容OpenAI接口的LLM服务的客户端。"""
    def __init__(self, model: str, api_key: str, base_url: str):
        self.model = model
        self.client = OpenAI(api_key=api_key, base_url=base_url)

    def generate(self, prompt: str, system_prompt: str) -> str:
        print("正在调用大语言模型...")
        try:
            messages = [
                {'role': 'system', 'content': system_prompt},
                {'role': 'user', 'content': prompt}
            ]
            response = self.client.chat.completions.create(
                model=self.model, messages=messages, stream=False
            )
            answer = response.choices[0].message.content
            print("大语言模型响应成功。")
            return answer
        except Exception as e:
            print(f"调用LLM API时发生错误: {e}")
            return "错误：调用语言模型服务时出错。"
```

配置：

```python
API_KEY   = "YOUR_API_KEY"
BASE_URL  = "YOUR_BASE_URL"
```

### 1.3.6 主循环（Agent Loop 的最小实现）

```python
# --- 初始化 ---
user_prompt = "你好，请帮我查询一下今天北京的天气，然后根据天气推荐一个合适的旅游景点。"
prompt_history = [f"用户请求: {user_prompt}"]

# --- 主循环 ---
for i in range(5):                       # 最大循环次数，防止死循环
    print(f"--- 循环 {i+1} ---\n")

    # ① 构建 Prompt
    full_prompt = "\n".join(prompt_history)

    # ② 调用 LLM 进行思考
    llm_output = llm.generate(full_prompt, system_prompt=AGENT_SYSTEM_PROMPT)

    # 模型可能输出多余 Thought-Action，需截断
    match = re.search(
        r'(Thought:.*?Action:.*?)(?=\n\s*(?:Thought:|Action:|Observation:)|\Z)',
        llm_output, re.DOTALL)
    if match:
        truncated = match.group(1).strip()
        if truncated != llm_output.strip():
            llm_output = truncated
            print("已截断多余的 Thought-Action 对")
    prompt_history.append(llm_output)

    # ③ 解析并执行行动
    action_match = re.search(r"Action: (.*)", llm_output, re.DOTALL)
    if not action_match:
        observation = "错误: 未能解析到 Action 字段。请确保严格遵循 'Thought: ... Action: ...' 格式。"
        prompt_history.append(f"Observation: {observation}")
        continue
    action_str = action_match.group(1).strip()

    # 结束条件
    if action_str.startswith("Finish"):
        final_answer = re.match(r"Finish\[(.*)\]", action_str).group(1)
        print(f"任务完成，最终答案: {final_answer}")
        break

    # 解析工具名与参数
    tool_name = re.search(r"(\w+)\(", action_str).group(1)
    args_str  = re.search(r"\((.*)\)", action_str).group(1)
    kwargs    = dict(re.findall(r'(\w+)="([^"]*)"', args_str))

    # 执行工具
    if tool_name in available_tools:
        observation = available_tools[tool_name](**kwargs)
    else:
        observation = f"错误：未定义的工具 '{tool_name}'"

    # ④ 记录观察结果
    prompt_history.append(f"Observation: {observation}")
```

### 1.3.7 运行案例分析（务必自己跑一遍）

以"查北京天气 → 按天气推荐景点"为例：
- **循环 1**：LLM 输出 `Thought: 用户想知道天气，需要调用天气工具 → Action: get_weather("北京")`，Observation = "北京当前天气：晴，气温 25 摄氏度"。
- **循环 2**：LLM 基于晴天推理 → `Action: get_attraction("北京", "晴")`，Observation = 景点列表。
- **循环 3**：LLM 认为信息足够 → `Action: Finish[今天北京晴朗……推荐前往颐和园……]`。

**关键观察**：当天气变成"雨"时，LLM 会自动推荐博物馆等室内景点——**代码里没有任何 `if 天气=晴 then 推荐颐和园` 的规则**。这种基于实时信息动态推理决策的能力，正是 Agent 的核心价值。

## 1.4 智能体应用的协作模式

### 1.4.1 作为开发者工具的智能体

- 增强人类工作流，**人始终在环内**：提出需求、审阅代码、决定采纳。
- 代表：GitHub Copilot、Cursor。
- 价值：把 AI 的推理/生成能力嵌入现有开发流程，提升人的效率。

### 1.4.2 作为自主协作者的智能体

- 能够独立完成**高层级目标**，多智能体分工协作。
- 代表框架：**CrewAI、MetaGPT、AgentScope**。
- 价值：把人从执行细节中解放出来，只需给出目标。

### 1.4.3 Workflow 与 Agent 的本质差异

> 一句话：**Workflow 是让 AI 按部就班地执行指令，Agent 则是赋予 AI 自由度去自主达成目标。**

| | **Workflow（工作流）** | **Agent（智能体）** |
|---|---|---|
| 本质 | 预先定义、结构化的**静态流程图** | 具备自主性、**以目标为导向**的系统 |
| 决策 | 在何种条件下、以何种顺序执行哪些操作都写死 | LLM 扮演"大脑"，理解环境、推理、制定计划、动态行动 |
| 典型案例 | 费用报销审批（<500 部门经理审批；>500 再走财务总监；通过后通知打款） | "查北京天气 → 按天气推荐景点"，无写死规则 |
| 优点 | 可控、可预测、可审计 | 灵活、适应开放场景、随环境实时变化 |
| 缺点 | 无法应对未覆盖的新情况 | 不确定、成本高、一致性难保证 |

**Agent 的动态推理示例**（旅行助手）：① 规划与工具调用（拆成查天气+推荐景点两步，自主选择并调用天气 API）→ ② 推理与决策（API 返回"晴朗微风"，LLM 推理"晴天适合户外"，筛选故宫/颐和园等）→ ③ 生成结果（综合成一段人性化回答）。若天气为"雨"，则自主改推室内场所。

## 1.5 智能体发展史（第 2 章）

### 1.5.1 基于符号与逻辑的早期智能体

- **物理符号系统假说**：智能的核心是对符号的操作与逻辑推理。
- **专家系统**：把领域专家的知识编码为规则库 + 推理机（"知识 + 推理"），在特定领域（如医疗诊断 MYCIN）表现优异。
- **SHRDLU**：能理解自然语言指令并在积木世界中行动，是符号主义的标志性成果。
- **符号主义面临的根本性挑战**：脆弱（现实充满模糊与例外，任何未覆盖的新情况都可能失效）+ **知识获取瓶颈**（把专家知识形式化极其昂贵）。

### 1.5.2 构建基于规则的聊天机器人

- **ELIZA**（1966，Weizenbaum）的设计思想：不"理解"语言，而是通过**模式匹配 + 文本替换**模拟对话（如把用户输入"我很累"映射为"你为什么觉得累？"）。
- 核心逻辑：关键词识别 → 规则替换 → 生成回应。
- 局限：无理解、无记忆、无世界知识，本质是"鹦鹉学舌"。**它的意义在于第一次让人类直观感受到"对话式交互"的可能**。

### 1.5.3 马文·明斯基的"心智社会"

- **对单一整体智能模型的反思**：智能不是由某个中心化的、全知全能的结构产生的。
- **作为协作体的智能**：复杂的整体智能可以从**大量简单局部单元的交互中涌现（emerge）**。
- **对多智能体系统的理论启发**：这是现代多智能体系统（MAS）与"多 Agent 协作"思想的哲学源头。

### 1.5.4 学习范式的演进与现代智能体

**（1）从符号到联结**：反向传播算法（辛顿等推动）为神经网络复苏奠基 → 深度学习时代到来，CNN/Transformer 成为主流，赋予智能体**感知世界**的能力。

**（2）基于强化学习的智能体**（行为主义）：强调通过与环境的互动与试错来学习最优策略。从 TD-Gammon 到 AlphaGo，为智能体赋予**从经验中习得复杂决策行为**的能力。

**（3）基于大规模数据的预训练**：在数 TB 文本上自监督学习，为 LLM 提供前所未有的**世界知识**与**通用推理能力**。

**（4）基于大语言模型的智能体**（图 2.10 的架构）：

LLM 智能体通过一个由多个模块协同工作的、持续迭代的闭环流程完成任务：

```
感知模块 ──Observation──┐
                        ▼
            ┌──────────────────────────────┐
            │ 规划模块（Reflection /         │
            │ Self-criticism，分解宏观目标） │
            └──────────┬───────────────────┘
                       ▼
                  LLM（认知中枢） ←→ 记忆模块（Memory）
                       │ 决策出 Tool Call
                       ▼
              执行模块 → 工具箱（Tool Use）→ 与外部环境交互
                       │
                       └→ Tool Result + 新环境状态 = 新 Observation
                          （同时更新 Memory）→ 启动下一轮循环
```

四步详解：
1. **感知**：感知模块从外部环境接收原始输入，形成 Observation（用户指令、API 返回值、环境状态变化）。
2. **思考**：**规划模块**做高级策略制定，通过**反思（Reflection）**与**自我批判（Self-criticism）**把宏观目标分解为具体可执行步骤；**LLM** 接收指令并与**记忆模块**交互整合历史信息，深度推理，决策出下一步操作（通常表现为一个 **Tool Call**）。
3. **行动**：**执行模块**解析指令，从**工具箱**中选择并调用合适工具（代码执行器、搜索引擎、API）与环境交互。
4. **观察与循环**：工具返回 **Tool Result** 给 LLM（对行动效果的直接反馈）；行动也改变了环境状态。两者共同构成新一轮 Observation，被感知模块再次捕获，LLM 同时**更新记忆**，启动下一轮"感知-思考-行动"。

**（5）智能体发展关键节点概览——三大思潮**

| 思潮 | 代表 | 核心主张 | 代表成果 |
|---|---|---|---|
| **符号主义** | 西蒙、明斯基 | 智能的核心在于对符号的操作与逻辑推理 | SHRDLU、专家系统、深蓝 |
| **联结主义** | 辛顿等 | 灵感源于对大脑神经网络的模拟 | 反向传播、CNN、Transformer |
| **行为主义** | —— | 通过与环境的互动和试错学习最优策略 | TD-Gammon、AlphaGo |

**汇流**：进入 21 世纪 20 年代，这些思想以前所未有的方式深度融合——以 GPT 系列为代表的 LLM 本身是**联结主义的产物**，却成为执行**符号推理**、进行工具调用和规划决策的核心"大脑"，形成**神经-符号结合的现代智能体架构**。

## 1.6 必须掌握 / 易踩的坑

- ✅ Agent Loop 四阶段：感知 → 思考（规划 + 工具选择）→ 行动 → 观察（+ 环境反馈）。
- ✅ PEAS 四要素：性能度量、环境、执行器、传感器。
- ✅ 三个分类维度：决策方式、反应 vs 规划、知识表示（亚符号/符号/神经符号）。
- ✅ LLM 智能体 = 混合式 + 神经符号主义；四大组件 = 模型、记忆、规划、工具。
- ✅ System Prompt 四要素：角色 / 工具清单 / 输出格式 / 结束条件。
- ✅ Workflow 与 Agent 的本质差异。
- ⚠️ 工具函数**不要抛异常**，返回错误字符串让模型自我修正。
- ⚠️ 主循环必须有**最大迭代次数**上限，否则可能死循环烧钱。
- ⚠️ 用正则解析 LLM 输出很脆弱（第 4 章习题专门讨论）——生产环境优先用原生 Function Calling。
- ⚠️ `prompt_history` 会不断增长，最终撞上下文窗口——这正是第 8/9 章"记忆 + 上下文工程"要解决的问题。
- ⚠️ 环境是**部分可观察**的，智能体必须设计"记忆 + 探索"机制。
