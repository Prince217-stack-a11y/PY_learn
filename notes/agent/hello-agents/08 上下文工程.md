# 08 上下文工程

> **教材**：第 9 章《上下文工程》
> **源码**：`code/chapter9/`（`hello_agents/context/`、`tools/builtin/{note_tool.py, terminal_tool.py}`）、`code/chapter9/project/`
> **一句话**：提示工程关心"**怎么写好这段话**"，上下文工程关心"**这一次推理，模型的窗口里到底该放哪些 token**"——本章把上下文工程变成可运行的代码（ContextBuilder / NoteTool / TerminalTool）。

---

## 8.1 什么是上下文工程（第 9.1 节）

**上下文 = 对 LLM 采样时包含的那组 tokens。** 手头的工程问题，是在 LLM 的固有约束下，**优化这些 tokens 的效用**，以便稳定地得到预期结果。

**核心提问**：*"什么样的上下文配置，最有可能让模型产出我们期望的行为？"*

**上下文工程是提示工程的自然演进**：

| | **提示工程（Prompt Engineering）** | **上下文工程（Context Engineering）** |
|---|---|---|
| 关注点 | 如何编写与组织 LLM 的指令以获得更优结果（系统提示写法、结构化策略） | 在**推理阶段**，如何策划与维护"**最优的信息集合（tokens）**" |
| 范围 | 提示本身 | 提示 + 系统指令 + 工具 + MCP + 外部数据 + 消息历史 + 检索结果 |
| 适用 | 单轮分类、文本生成 | 多轮、长时程、跨多次推理轮次运行的智能体 |

**为什么提示工程不够用了**：随着工程化地构建更强的智能体，它们在**更长的时间范围内、跨多次推理轮次**地工作，就需要能管理**整个上下文状态**的策略。一个循环运行的智能体会不断产生下一轮推理可能相关的数据，这些信息**必须被周期性地提炼**。

> 上下文工程的"艺与术"，在于从持续扩张的"候选信息宇宙"中，**甄别哪些内容应当进入有限的上下文窗口**。

**关键心法**：想有效驾驭 LLM，往往需要"**在上下文中思考**"——在任何一次调用时，都要审视 LLM 可见的整体状态，并预判这种状态可能诱发的行为。

## 8.2 为什么上下文工程重要（第 9.2 节）

### 8.2.1 上下文腐蚀（Context Rot）

针堆找针（needle-in-a-haystack）类基准揭示一个现象：**随着上下文窗口中的 tokens 增加，模型从上下文中准确回忆信息的能力反而下降**。

- 不同模型的退化曲线或许更平滑，但这一特征**几乎在所有模型上都会出现**。
- 结论：**"上下文必须被视作一种有限资源，且具有边际收益递减。"**
- 类比：像人类有限的工作记忆容量一样，LLM 也有一笔"**注意力预算**"——每新增一个 token，都会消耗这笔预算的一部分。

### 8.2.2 稀缺来自架构约束（理解这一点才算懂）

- Transformer 让每个 token 与上下文中的**所有** token 建立关联，理论上形成 $n^2$ 级的**两两注意力关系**。
- 随着上下文长度增长，模型对这些两两关系的建模能力会被"**拉薄**"，从而自然产生"上下文规模"与"注意力集中度"的张力。
- 模型的注意力模式来源于训练数据分布——**短序列通常比长序列更常见**，因此模型对"全上下文依赖"的经验更少、专门参数也更少。
- 位置编码插值（position encoding interpolation）等技术可以让模型推理时"适配"比训练期更长的序列，但**会牺牲部分对 token 位置的精确理解**。

> 总结：这些因素共同形成的是一个**性能梯度**（渐进下降），而**不是"悬崖式"崩溃**——模型在长上下文下依旧强大，但相较短上下文，在信息检索与长程推理上的精度会有所下降。

### 8.2.3 有效上下文的"解剖学"（第 9.2.1 节）

**目标**：**"用尽可能少、但高信号密度的 tokens，最大化获得期望结果的概率。"**
**总原则**：**信息充分但紧致**。

**三个组件**：

**① 系统提示（System Prompt）**
- 语言清晰、直白，信息层级把握在"**刚刚好**"的高度。
- **两极误区**：
  - **过度硬编码**：在提示中写入复杂、脆弱的 if-else 逻辑，长期维护成本高、易碎。
  - **过于空泛**：只给宏观目标与泛化指引，缺少对期望输出的**具体信号**，或假定了错误的"共享上下文"。
- **建议**：将提示**分区组织**（如 `<background_information>`、`<instructions>`、工具指引、输出描述等），用 XML/Markdown 分隔；追求能完整勾勒期望行为的"**最小必要信息集**"（**注意"最小"并不等于"最短"**）。
- **工作流**：先用最好的模型在最小提示上试跑，再依据失败模式增补清晰的指令与示例。

**② 工具（Tools）**
- 工具定义了智能体与信息/行动空间的**契约**，必须促进效率：既要返回 **token 友好**的信息，又要鼓励高效的智能体行为。
- 工具应当：**职责单一、相互低重叠、接口语义清晰**；**对错误鲁棒**；**入参描述明确、无歧义**，充分发挥模型擅长的表达与推理能力。
- 避免"**臃肿的工具集**"。

**③ 示例（Examples）**
- **多样且典型**——用"典型示例"锚定行为，用"边界示例"防止过拟合。

### 8.2.4 JIT 上下文与智能体式搜索（第 9.2.2 节）

> **一个简洁的定义：智能体 = 在循环中自主调用工具的 LLM。**

工程实践正从"**推理前一次性检索**（embedding 检索）"逐步过渡到"**及时（Just-in-time, JIT）上下文**"：

- 不再预先加载所有相关数据，而是维护**轻量化引用**（文件路径、存储查询、URL 等），在运行时通过工具动态加载所需数据。
- 这让模型可以撰写针对性查询、缓存必要结果，并用 `head` / `tail` 之类命令分析大体量数据——**无需把整块数据一次性塞入上下文**。
- 认知模式更贴近人类：我们不会死记硬背全部信息，而是用文件系统、收件箱、书签等**外部索引按需提取**。
- **引用的元数据本身也在精化行为**：目录层级、命名约定、时间戳等都在隐含传达"目的与时效"。例如 `tests/test_utils.py` 与 `src/core/test_utils.py` 的语义暗示就不同。
- 由此实现**渐进式披露（Progressive Disclosure）**：每一步交互都会产生新的上下文，反过来指导下一步决策——文件大小暗示复杂度、命名暗示用途、时间戳暗示相关性。智能体得以按层构建理解，只在工作记忆中保留"当前必要子集"，并用"记笔记"的方式做补充持久化。

⚠️ **权衡**：运行时探索往往比预计算检索**更慢**，且需要"有主见"的工程设计来确保模型拥有正确的工具与启发式。如果缺少引导，智能体可能会误用工具、追逐死胡同或错过关键信息，造成上下文浪费。

✅ **混合策略常更有效**：前置加载少量"高价值"上下文以保证速度，然后允许智能体按需继续自主探索。
- 边界的选择取决于任务动态性与时效要求。
- 工程上可以预先放入类似"项目约定说明（如 README/指南）"的文件，同时提供 `glob`、`grep` 等原语，让智能体即时检索具体文件，从而绕开过时索引与复杂语法树的沉没成本。

### 8.2.5 面向长时程任务的上下文工程（第 9.2.3 节）

长时程任务要求智能体在超出上下文窗口的长序列行动中，仍保持连贯性、上下文一致与目标导向（如大型代码库迁移、跨数小时的系统性研究）。**指望无限增大上下文窗口并不能根治"上下文污染"与相关性退化**，因此需要三种直接面向约束的工程手段：

| 策略 | 定义与做法 | 关键点 |
|---|---|---|
| **压缩整合（Compaction）** | 当对话接近上下文上限时，对其进行**高保真总结**，并用该摘要**重启一个新的上下文窗口**，以维持长程连贯性 | 新窗口 = **压缩摘要 + 最近少量高相关工件** |
| **结构化笔记（Structured Note-taking）** | 以固定频率把关键信息写入**上下文之外的持久化存储**（TODO、NOTES.md、结论/依赖/阻塞索引） | 用笔记做"外置记忆"，而不是全塞窗口 |
| **子代理架构（Sub-agent Architectures）** | 主代理负责规划与综合，**专长子代理在"干净的上下文窗口"深挖**，仅回传凝练摘要 | 摘要常见 1,000~2,000 tokens |

⚠️ 调参提示：**先优化召回，再优化精确度**；"轻触式"压缩即清理深历史中的工具调用与结果。

## 8.3 ContextBuilder：把上下文工程变成代码（第 9.3 节）

### 8.3.1 设计目标（四条）

统一入口、**稳定形态（固定骨架）**、**预算守护**、**最小规则**。
- **最小规则**：不引入来源/优先级等复杂分类维度，"统一以'相关性 + 新近性'的分数进行选择"。

### 8.3.2 固定分区骨架

```
[Role & Policies]   角色与行为准则
[Task]              任务
[State]             当前状态
[Evidence]          外部检索证据
[Context]           历史对话与记忆
[Output]            输出要求
```

实现中按 packet 的 `metadata["type"]` 分组输出五段（`[Role & Policies] / [Task] / [Evidence] / [Context] / [Output]`），用 `"\n\n"` 连接。
**优势**：可读性、可调试性、可扩展性（新增信息源只需新增分区）。

### 8.3.3 两个核心数据结构

```python
from dataclasses import dataclass, field

@dataclass
class ContextPacket:
    content: str
    timestamp: float
    token_count: int
    relevance_score: float = 0.5      # __post_init__ 把分数夹到 [0,1]
    metadata: dict = field(default_factory=dict)

@dataclass
class ContextConfig:
    max_tokens: int = 3000
    reserve_ratio: float = 0.2        # 确保系统指令不被挤占
    min_relevance: float = 0.1
    enable_compression: bool = True
    recency_weight: float = 0.3
    relevance_weight: float = 0.7     # 断言 recency_weight + relevance_weight == 1.0
```

### 8.3.4 GSSC 流水线（精华）

**Gather → Select → Structure → Compress**

**① Gather（收集）**
- 系统指令：`relevance_score=1.0`（"始终保留"，不参与评分，标记 `priority: high`）。
- 记忆检索：`action=search, limit=10, min_importance=0.3`。
- RAG 检索：`limit=5, min_score=0.3`。
- 对话历史：**只取最近 5 条**，基础相关性 0.6。
- `custom_packets` 追加自定义内容。
- **每个外部源都用 try-except 包裹**以保证容错。

**② Select（筛选）**

```python
# 先分离系统指令并扣除其 tokens；剩余预算 <= 0 时只返回系统指令
remaining_tokens = max_tokens * (1 - reserve_ratio) - system_tokens

combined_score = relevance_weight * relevance + recency_weight * recency
# 低于 min_relevance 的过滤；按分数降序「贪心填充」直到 token 上限

# 相关性：关键词重叠（Jaccard 相似度）
relevance = len(intersection) / len(union)
# 新近性：指数衰减，限制在 [0.1, 1.0]
recency = max(0.1, min(1.0, math.exp(-0.1 * age_hours / 24)))
```

**③ Structure（结构化）**：按类型分组拼装固定模板。

**④ Compress（压缩，兜底）**
- `current_tokens <= max_tokens` → 直接返回。
- 否则按 `"\n\n"` 分区累加保留，剩余预算 < 50 tokens 则 `break`，截断处追加 `[... 内容已压缩 ...]`。
- `_truncate_text` 按"字符/token 比例"估算截断。

⚠️ **Token 计数说明**：`_count_tokens` 用"**中文 1 字符 ≈ 1 token，英文 1 单词 ≈ 1.3 tokens**"估算；注释明确**生产环境应使用真实 tokenizer**。

### 8.3.5 集成方式

```python
class ContextAwareAgent(SimpleAgent):
    def run(self, user_input, **kwargs):
        optimized_context = self.builder.build(
            user_query=user_input,
            conversation_history=self.get_history(),
            system_instructions="你是一位资深的Python数据工程顾问…",
        )
        messages = [
            {"role": "system", "content": optimized_context},
            {"role": "user", "content": user_input},
        ]
        # 调用 LLM，并把交互摘要写回 memory_tool
        ...
```

使用方式：

```python
from hello_agents.context import ContextBuilder, ContextConfig

config = ContextConfig(max_tokens=3000, reserve_ratio=0.2,
                       min_relevance=0.2, enable_compression=True)
builder = ContextBuilder(memory_tool=memory_tool, rag_tool=rag_tool, config=config)
context = builder.build(user_query="如何优化Pandas的内存占用?",
                        conversation_history=conversation_history,
                        system_instructions="你是一位资深的Python数据工程顾问…")
```

### 8.3.6 五条改进建议（第 9.3.5 节）

动态调整 token 预算；把关键词重叠替换为**向量相似度**；对不变的系统指令与知识库内容做**缓存**；记录**上下文构建统计**（选中数量、token 使用率）；对相关性/新近性权重做 **A/B 测试**。

## 8.4 NoteTool：结构化笔记（第 9.4 节）

**定位**：为长时程任务提供"**结构化外部记忆**"，以 Markdown 文件为载体。

与 `MemoryTool`（对话式记忆：工作/情景/语义）互补——NoteTool 补足**"项目式任务"的长期追踪**。

**文件格式**：**YAML 前置元数据 + Markdown 正文**。
**ID 规则**：`note_{YYYYmmdd_HHMMSS}_{索引}`，**文件名即 ID**。
**索引**：同时维护 `notes_index.json` 用于快速检索、集中元数据管理与完整性校验。

**七个核心操作**：`create` / `read` / `update` / `search` / `list` / `summary` / `delete`
**`note_type` 取值**：`task_state` / `conclusion` / `blocker` / `action` / `reference` / `general`

```python
from hello_agents.tools import NoteTool

notes = NoteTool(workspace="./project_notes")
note_id = notes.run({
    "action": "create",
    "title": "重构项目 - 第一阶段",
    "content": "## 完成情况\n…",
    "note_type": "task_state",
    "tags": ["refactoring", "phase1"],
})
```

**与 ContextBuilder 集成**：在 `run()` 中先 `list(note_type="blocker", limit=2)` 再 `search(query)`，合并去重后转成 `ContextPacket`（`token_count=len(content)//4`、`relevance_score=0.75`），通过 `custom_packets=` 注入。

**五个优势**：结构化记录、**版本友好**（纯文本天然支持 Git）、低开销、灵活分类（`type` + `tags`）、人机协作友好（Markdown 可手改）。

**五条最佳实践（第 9.4.5 节）**：
1. **合理分类**（`task_state`/`conclusion`/`blocker`/`action`/`reference`）。
2. **定期清理归档**（已解决的 blocker 更新为 conclusion、过时 action 删除或更新、用 tags 做版本管理如 `["v1.0","completed"]`）。
3. **与 ContextBuilder 配合**（每轮检索、按类型设不同相关性 : blocker > action > conclusion、限制笔记数量）。
4. **人机协作**（Markdown 可手改、Git 版本控制、关键阶段人工审核）。
5. **自动化工作流**（摘要报告、进度文档、同步 Notion/Confluence）。

## 8.5 TerminalTool：即时文件系统访问（第 9.5 节）

**定位**：提供"**安全的命令行执行能力**"，实现 **JIT 即时上下文**——**不预先索引整个代码库，而是按需探索**（`find`、`tail|grep`、`head`、`wc` 等）。

### 8.5.1 四层安全机制（本节精华）

1. **命令白名单**：

```python
ALLOWED_COMMANDS = {
    "ls", "dir", "tree", "cat", "head", "tail", "less", "more",
    "find", "grep", "egrep", "fgrep", "wc", "sort", "uniq", "cut",
    "awk", "sed", "pwd", "cd", "file", "stat", "du", "df",
    "echo", "which", "whereis",
}
# 白名单外的命令立即拒绝（如 rm）
```
2. **工作目录限制（沙箱）**：用 `new_dir.relative_to(self.workspace)` 校验，`~` 映射到 workspace，**禁止 `..` 逃逸到工作目录外**。
3. **超时控制**：`timeout=30`。
4. **输出大小限制**：`max_output_size=10*1024*1024`，超出被截断。

> 效果：任何白名单外命令立即拒绝；**即使行为异常也无法影响工作目录外的系统**。

### 8.5.2 执行实现要点

`_execute_command`：用 `cwd` 在当前目录执行、**捕获并合并标准错误**、非零返回码标记为警告、超时与异常被妥善处理**不使智能体崩溃**。
`cd` 由 `_handle_cd` 特殊处理（`allow_cd` 开关、`.`/`..`/`~`、存在性与是否为目录校验）。

### 8.5.3 用法

```python
from hello_agents.tools import TerminalTool

terminal = TerminalTool(workspace="./my_project")
print(terminal.run({"command": "find . -name '*.py' -type f"}))
print(terminal.run({"command": "tail -n 100 /var/log/app.log | grep ERROR"}))
```

## 8.6 实战：代码库维护助手（第 9.6 节）

**三层架构**：

| 层 | 组件 | 作用 |
|---|---|---|
| 即时访问 | **TerminalTool** | 按需探索代码，不看全量 |
| 会话记忆 | **MemoryTool** | 记住当前会话的上下文 |
| 持久笔记 | **NoteTool** | 跨会话保留状态（task_state / blocker / action） |
| 筛选组织 | **ContextBuilder** | 每次调用前选出该进入窗口的 tokens |

**可扩展方向（第 9.6.5 节）**：集成 RAGTool 建代码向量索引、拆分"探索者/分析者/规划者"子代理、集成测试工具、用 TerminalTool 执行 git、加 Gradio/Streamlit 界面。

## 8.7 必须掌握 / 易踩的坑

- ✅ 上下文工程 vs 提示工程的区别；上下文是**有限资源**。
- ✅ 上下文腐蚀 + 架构原因（n² 注意力被拉薄、短序列更常见）。
- ✅ 有效上下文三组件 + "信息充分但紧致"。
- ✅ JIT 上下文 + 渐进式披露；长时程三策略（Compaction / 笔记 / 子代理）。
- ✅ ContextBuilder 的 GSSC 四步 + 五段骨架 + 相关性(0.7)/新近性(0.3) 加权。
- ✅ NoteTool 七操作 + 六种 note_type；TerminalTool 的四层安全机制。
- ⚠️ 系统提示的两极误区：过度硬编码 vs 过于空泛。
- ⚠️ 工具集不要臃肿；工具要返回 token 友好的信息。
- ⚠️ ContextBuilder 用字符比例估算 token，**生产环境要换真实 tokenizer**。
- ⚠️ JIT 探索比预计算检索慢，需要有"主见"的设计引导。
- ⚠️ 压缩要先保召回再保精确度；长时程任务别指望"窗口大就够"。

## 8.8 一页速查（Q&A 自测）

1. 上下文工程的定义？→ 推理阶段策划与维护最优 tokens 集合。
2. 什么是上下文腐蚀？→ 窗口越大，准确回忆信息的能力反而下降。
3. 为什么会有注意力预算？→ n² 注意力被拉薄 + 训练以短序列为主。
4. JIT 上下文的核心做法？→ 维护轻量引用，运行时按需加载。
5. 长时程任务三策略？→ 压缩整合、结构化笔记、子代理架构。
6. ContextBuilder 的四步？→ Gather / Select / Structure / Compress。
7. 相关性/新近性默认权重？→ 0.7 / 0.3。
8. ContextBuilder 的五段骨架？→ Role & Policies / Task / Evidence / Context / Output。
9. TerminalTool 四层安全机制？→ 白名单、目录沙箱、超时、输出大小限制。
10. NoteTool 七操作？→ create/read/update/search/list/summary/delete。
11. NoteTool 与 MemoryTool 的分工？→ NoteTool 管项目式长期追踪；MemoryTool 管对话式记忆。
12. 混合策略为什么常更有效？→ 前置少量高价值上下文保速度，再按需自主探索保灵活。
