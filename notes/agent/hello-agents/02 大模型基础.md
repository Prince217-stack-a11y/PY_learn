## 2.1 语言模型与 Transformer 架构（第 3.1 节）

### 2.1.1 从 N-gram 到 RNN

| 模型 | 思路 | 问题 |
|---|---|---|
| **N-gram** | 用统计方法估计"前 n-1 个词后面接某词"的概率，$P(w_t \mid w_{t-n+1}, \dots, w_{t-1})$ | **短视**（只看固定窗口）、**数据稀疏**（未见过的组合概率为 0） |
| **RNN** | 引入循环结构与隐藏状态，理论上可捕捉任意长距离依赖 | **串行计算**（第 t 步必须等第 t-1 步）→ 无法大规模并行、长序列效率低、梯度消失 |
| **LSTM** | 用门控机制缓解梯度消失 | 仍是串行，瓶颈未解 |

**实践建议**：`code/chapter3/N_gram.py` 用几十行实现了 N-gram，跑一遍能直观感受"为什么统计语言模型不够用"；`Word_Embedding.py` 则演示了词向量如何把离散符号变成可计算向量。

### 2.1.2 Transformer 架构解析

Transformer（2017，谷歌团队）**完全抛弃循环结构，转而完全依赖"注意力（Attention）"机制**捕捉序列内依赖关系，从而实现真正的**并行计算**。

**（1）Encoder-Decoder 整体结构**

最初为端到端机器翻译设计，宏观上遵循经典的**编码器-解码器**架构，可理解为一个分工明确的团队：
- **编码器（Encoder）**：任务是"**理解**"输入整个句子，为每个词元生成富含上下文信息的向量表示。
- **解码器（Decoder）**：任务是"**生成**"目标句子，参考自己已生成的前文，并"咨询"编码器的理解结果，生成下一个词。

**（2）核心组件（`code/chapter3/Transformer.py` 约 10KB 的完整实现）**

| 组件 | 作用 |
|---|---|
| **位置编码（Positional Encoding）** | 自注意力本身对顺序不敏感，必须额外注入位置信息（用正弦/余弦函数或可学习参数） |
| **多头注意力（Multi-Head Attention）** | 把 Query/Key/Value 投影到多个子空间并行做注意力，再拼接——让模型在不同"表示子空间"同时关注不同关系 |
| **掩码自注意力（Masked Self-Attention）** | 在解码器中防止"偷看"未来词元（见下） |
| **交叉注意力（Cross-Attention）** | 解码器对编码器输出的注意力（"咨询"输入句子的理解结果） |
| **位置前馈网络（Position-Wise FFN）** | 对每个位置独立做非线性变换（通常是两层 MLP），提供非线性表达能力 |
| **残差连接 + 层归一化（Residual + LayerNorm）** | 每个子层都是 `norm(x + dropout(sublayer(x)))`，保证深层网络可训练、梯度稳定 |

**编码器层**与**解码器层**的结构差异：

```python
class EncoderLayer(nn.Module):
    def forward(self, x, mask):
        attn_output = self.self_attn(x, x, x, mask)          # 多头自注意力
        x = self.norm1(x + self.dropout(attn_output))         # 残差 + 层归一化
        ff_output = self.feed_forward(x)                      # 前馈网络
        x = self.norm2(x + self.dropout(ff_output))
        return x

class DecoderLayer(nn.Module):
    def forward(self, x, encoder_output, src_mask, tgt_mask):
        attn_output = self.self_attn(x, x, x, tgt_mask)                       # ① 掩码自注意力（对自己）
        x = self.norm1(x + self.dropout(attn_output))
        cross_attn_output = self.cross_attn(x, encoder_output, encoder_output, src_mask)
        x = self.norm2(x + self.dropout(cross_attn_output))                   # ② 交叉注意力（对编码器）
        ff_output = self.feed_forward(x)
        x = self.norm3(x + self.dropout(ff_output))                           # ③ 前馈网络
        return x
```

### 2.1.3 Decoder-Only 架构（当今主流）

Transformer 的设计哲学是"**先理解，再生成**"。但 OpenAI 开发 GPT 时提出更简单的思想：**语言的核心任务，不就是预测下一个最有可能出现的词吗？** 于是**完全抛弃编码器，只保留解码器**——这就是 **Decoder-Only** 架构的由来。

**工作模式：自回归（Autoregressive）**——本质是"文字接龙"：
1. 给模型起始文本（如 "Datawhale Agent is"）。
2. 模型预测下一个最可能的词（如 "a"）。
3. 把刚生成的词追加到输入末尾（"Datawhale Agent is a"）。
4. 基于新输入再预测下一个词（如 "powerful"）。
5. 重复，直到生成完整句子或达到停止条件。

**训练时如何保证不"偷看"未来？——掩码自注意力（关键机制）**：
- 训练时整段文本可被**并行**送入模型；在自注意力算出分数矩阵后、Softmax 归一化**之前**，模型应用一个**因果掩码**，把所有位于当前位置**之后**的词元对应分数替换为一个极大的负数。
- 该矩阵过 Softmax 后，这些位置的概率变为 0 → **从数学上阻止模型关注它后面的信息**。
- 生成阶段更直接：未来词元尚未生成，模型只能把已生成内容当上下文，一步步预测。
- 掩码自注意力保证**训练时的学习方式与生成时的自回归使用方式一致**，模型始终只依赖当前位置之前的信息。

**Decoder-Only 的三大优势**：
- **训练目标统一**：唯一任务是"预测下一个词"，非常适合在海量无标注文本上预训练。
- **结构简单、易于扩展**：更少组件 → 易于规模化（GPT-4、Llama 等千亿/万亿参数巨型模型都基于此）。
- **天然适合生成任务**：自回归模式与对话、写作、代码生成等所有生成式任务完美契合——这是它成为通用智能体基础的核心原因。

## 2.2 与大语言模型交互（第 3.2 节）——工程重点

### 2.2.1 提示工程：采样参数

把 LLM 比作能力极强的"大脑"，**提示（Prompt）**就是与它沟通的语言。提示工程研究如何设计精准的提示引导模型产生期望输出。**对智能体而言，精心设计的提示能让多 Agent 协作分工高效。**

**采样参数的本质**：Softmax 给出概率分布 $p_i = e^{z_i}/\sum_j e^{z_j}$；采样参数就是在此基础上按不同策略"重新调整"或"截断"分布，从而改变下一个 token。

**Temperature（温度）**——控制输出的"随机性"与"确定性"：

$$p_i^{(T)} = \frac{e^{z_i / T}}{\sum_{j=1}^{k} e^{z_j / T}}$$

- T 变小 → 分布"更陡峭"，高概率项权重放大 → 更保守、重复率高。
- T 变大 → 分布"更平坦"，低概率项权重提升 → 更多样、可能不连贯。

**温度分级（背下来）**：

| 温度 | 输出风格 | 适用场景 |
|---|---|---|
| **低（0 ≤ T < 0.3）** | 精准、确定 | 事实性任务（问答、数据计算、代码生成）；严谨性场景（法律条文解读、技术文档、学术概念解释） |
| **中（0.3 ≤ T < 0.7）** | 平衡、自然 | 日常对话（客服、聊天机器人）；常规创作（邮件、产品文案、简单故事） |
| **高（0.7 ≤ T < 2）** | 创新、发散 | 创意性任务（诗歌、科幻故事、广告 slogan、艺术灵感）；发散性思考 |

**Top-k**：把所有 token 按概率从高到低排序，取排名前 k 个组成"候选集"，再归一化：$\hat p_i = p_i / \sum_{j\in候选集} p_j$。
- 与温度的区别：温度调整**所有** token 的分布陡峭程度，**不改变候选数量**；Top-k **限制候选数量**（只保留前 k 个）再采样。
- **k=1 时输出完全确定，退化为"贪心采样"**。

**Top-p（核采样）**：按概率降序累加，直到累积和首次达到或超过阈值 p，累加过程中包含的所有 token 组成"核集合"，再归一化。
- 与 Top-k 的区别：Top-k 是**固定截断大小**；Top-p 能**动态适应不同分布的长尾特性**，对概率分布不均匀的极端情况适应性更好。

**协同工作与优先级**：同时设置时按**分层过滤**协作，优先级顺序为 **温度调整 → Top-k → Top-p**。
- 温度调整整体分布陡峭程度 → Top-k 先保留概率最高的 k 个候选 → Top-p 再从 Top-k 结果中选累积概率 ≥ p 的最小集合。
- 通常 **Top-k 和 Top-p 二选一即可**；若同时设置，实际候选集为两者的**交集**。

**两个极端情况**：
- 温度设为 0：Top-k / Top-p 都变得无关紧要（最高概率 token 必被选中）。
- Top-k 设为 1：温度 / Top-p 也都无关紧要（只有一个 token 通过 Top-k）。

> **做 Agent 的默认建议**：工具调用 / 结构化输出用**低温度（0~0.2）**；创意文案用中高温度。Top-k 与 Top-p 二选一即可。

### 2.2.2 提示工程的三种示例方式

以情感分类任务（判断文本情感为正面/负面/中性）为例：

```python
# 零样本提示（Zero-shot）：不给任何示例，靠模型泛化能力
文本: Datawhale的AI Agent课程非常棒！
情感: 正面

# 单样本提示（One-shot）：给 1 个完整示例，展示任务格式与期望输出风格
文本: 这家餐厅的服务太慢了，等了一个小时。 → 情感: 负面
文本: Datawhale的AI Agent课程非常棒！        → 情感:

# 少样本提示（Few-shot）：给多个示例，覆盖不同类别与边界情况
```

**选择原则**：
- 任务通用、模型能力强 → **Zero-shot** 最省 token。
- 输出格式严格（要 JSON / 特定标签） → **Few-shot** 最稳。
- 少量示例即可大幅提升一致性——"**对 LLM 而言，好的示例胜过千言万语**"。

> 第 5~16 章的工程实践几乎全用"角色 + 任务 + 输出格式 + 示例"的**结构化提示词**，本质是 Few-shot 的工程化版本。

### 2.2.3 文本分词（Tokenization）

**为什么不能直接用"字符"或"单词"？**
- 字符级：序列太长，语义单元太小，模型难以捕捉词级信息。
- 单词级：词表会爆炸，且无法处理未登录词（OOV）。

**BPE（Byte Pair Encoding）三步**：
1. 把所有词拆成**字符**，词尾加 `</w>` 表示结束。
2. 统计所有相邻字符对的频率，把**最高频**的一对合并为新词元加入词表。
3. 重复第 2 步，直到词表大小达到预设阈值。

**迷你演示**（语料 `{hug:1, pug:1, pun:1, bun:1}`，目标词表大小 10）：

```python
import re, collections

def get_stats(vocab):
    """统计词元对频率"""
    pairs = collections.defaultdict(int)
    for word, freq in vocab.items():
        symbols = word.split()
        for i in range(len(symbols) - 1):
            pairs[symbols[i], symbols[i+1]] += freq
    return pairs

def merge_vocab(pair, v_in):
    """合并词元对"""
    v_out = {}
    bigram = re.escape(' '.join(pair))
    p = re.compile(r'(?<!\S)' + bigram + r'(?!\S)')
    for word in v_in:
        w_out = p.sub(''.join(pair), word)
        v_out[w_out] = v_in[word]
    return v_out

# 每个词末尾加 </w> 表示结束，并切分好字符
vocab = {'h u g </w>': 1, 'p u g </w>': 1, 'p u n </w>': 1, 'b u n </w>': 1}

for i in range(4):
    pairs = get_stats(vocab)
    if not pairs:
        break
    best = max(pairs, key=pairs.get)
    vocab = merge_vocab(best, vocab)
    print(f"第{i+1}次合并: {best} -> {''.join(best)}")

# 输出：
# 第1次合并: ('u', 'g') -> ug
# 第2次合并: ('ug', '</w>') -> ug</w>
# 第3次合并: ('u', 'n') -> un
# 第4次合并: ('un', '</w>') -> un</w>
```

**推理示例**：词表训练完成后，对未见过的 "bug" 分词——先查 "bug"（不在）→ 查 "bu"（不在）→ 查 "b" 和 "ug"（都在）→ 切分为 `['b', 'ug']`。

**后续优化算法**：
- **WordPiece**（Google BERT 采用）：与 BPE 相似，但合并标准不是"最高频率"，而是"**能最大化提升语料库的语言模型概率**"——优先合并让整个语料库"通顺度"提升最大的词元对。
- **SentencePiece**（Google 开源，Llama 采用）：最大特点是**把空格也视作普通字符**（通常用下划线 `_` 表示），使**分词和解码过程完全可逆，且不依赖特定语言**（不需要知道中文不用空格分词）。

**分词对智能体开发者的三大实际影响（很重要）**：
1. **上下文窗口限制**：模型的上下文窗口（如 8K、128K）是以 **Token 数量**计算的，不是字符数或单词数。同一段话在不同语言（中英文）或不同分词器下，Token 数量可能相差巨大。精确管理输入长度、避免超限，是构建长时记忆智能体的基础。
2. **API 成本**：大多数模型 API 按 Token 数量计费。了解文本会被如何分词，是预估和控制智能体运行成本的关键。
3. **模型表现的异常**：有时模型奇怪的表现根源在于分词。例如模型擅长算 `2 + 2`，但对 `2+2`（无空格）就可能出错（后者可能被视为一个独立的不常见词元）；同一词因首字母大小写不同，也可能被切成完全不同的 Token 序列。设计提示词与解析输出时要考虑这些"陷阱"。

### 2.2.4 调用开源大语言模型

**本地快速验证（Hugging Face Transformers）**——`code/chapter3/Qwen.py`：

```python
from transformers import AutoModelForCausalLM, AutoTokenizer

model_name = "Qwen/Qwen3-0.6B"          # 参数量小，适合本地尝鲜
tokenizer = AutoTokenizer.from_pretrained(model_name)
model = AutoModelForCausalLM.from_pretrained(model_name)

messages = [{"role": "user", "content": "你好，请介绍一下你自己。"}]
text = tokenizer.apply_chat_template(messages, tokenize=False, add_generation_prompt=True)
inputs = tokenizer(text, return_tensors="pt")
outputs = model.generate(**inputs, max_new_tokens=256, temperature=0.7, top_p=0.9)
print(tokenizer.decode(outputs[0][inputs["input_ids"].shape[1]:], skip_special_tokens=True))
```

> ⚠️ Transformers 本地推理"**非常适合入门学习和功能验证，但其底层实现在处理高并发请求时性能有限，通常不作为生产环境的首选方案**"。生产级本地部署用 **VLLM**（连续批处理、PagedAttention）或 **Ollama**（详见第 7 章）。
> 练习建议：部署一个轻量模型（推荐 Qwen3-0.6B），**调整采样参数并观察对输出的影响**；选一个具体任务（文本分类、信息抽取、代码生成），对比 Zero-shot / Few-shot / Chain-of-Thought 的效果差异。

### 2.2.5 模型的选择

选择模型**并非简单追求"最大、最强"**，而是在性能、成本、速度和部署方式之间权衡。8 个考量维度：

| 维度 | 要点 |
|---|---|
| **性能与能力** | 最核心。不同模型擅长任务不同（逻辑推理/代码 vs 创意写作/多语言）。参考公开基准榜（如 LMSys Chatbot Arena Leaderboard） |
| **成本** | 闭源看 API 调用费（按 Token 计费）；开源看本地部署的硬件（GPU/内存）与运维成本 |
| **速度（延迟）** | 实时交互（客服、游戏 NPC）关键。轻量级或优化模型（GPT-3.5 Turbo、Claude 3.5 Sonnet）延迟更优 |
| **上下文窗口** | 一次能处理的 Token 上限。长文档、代码库分析、长期对话记忆需 128K Token 或更高 |
| **部署方式** | API 最简单但数据发给第三方；本地部署确保隐私与自主可控，但对技术/硬件要求高 |
| **生态与工具链** | 主流模型有更丰富的社区支持、教程、微调工具、兼容框架（LangChain、LlamaIndex、HuggingFace），可加速开发、降低找答案的难度 |
| **可微调性与定制化** | 特定领域/任务需求 → 看模型的微调接口与工具是否便捷；开源模型灵活性通常更大 |
| **安全性与伦理** | 偏见、毒性、幻觉表现；服务商/社区在负责任 AI 上的投入。面向公众或涉敏感信息的应用不可忽视 |

**闭源模型概览（代表前沿，稳定易用的 API，构建高性能智能体首选）**：
- **OpenAI GPT 系列**：从 GPT-3（开启大模型时代）→ ChatGPT（引入 RLHF、与人类意图对齐）→ GPT-4（开启多模态时代）→ 最新 GPT-5（多模态与通用智能再提升，文本/音频/图像无缝处理，实时语音对话尤佳）。
- **Google Gemini 系列**：**原生多模态**代表，统一处理文本/代码/音视频/图像，以超长上下文窗口见长。Ultra（最强，复杂任务）/ Pro（高性能高效）/ Nano（设备端优化）；2.5 Pro、2.5 Flash 进一步提升推理与上下文窗口，Flash 以更快推理速度和成本效益适合快速响应。
- **Anthropic Claude 系列**：专注 AI 安全与负责任 AI，以**处理长文档、减少有害输出、遵循指令**的可靠性闻名，受企业级应用青睐。Claude 3：Opus（最强）/ Sonnet（性能速度平衡）/ Haiku（最快最紧凑）；Claude 4（如 Claude 4 Opus）在通用智能、复杂推理、代码生成上有显著进展。
- **国内主流闭源**：百度文心一言、腾讯混元、华为盘古、科大讯飞星火、月之暗面（Moonshot AI）等，中文处理有天然优势。

**开源模型概览（最高灵活性、透明度和自主性）**：
- **Meta Llama 系列**：开源重要里程碑。Llama 4（2025-04）首批采用**混合专家（MoE）架构**，通过仅激活处理特定任务所需的模型部分显著提升计算效率。Llama 4 Scout（1000 万 token 上下文，长文档分析+移动端）、Llama 4 Maverick（多模态，编码/复杂推理/多语言）、Llama 4 Behemoth（多项 STEM 基准超越对手，最强）。
- **Mistral AI 系列**：法国，以"**小尺寸、高性能**"著称。Mistral Medium 3.1（2025-08）在代码生成、STEM 推理、跨领域问答上准确率与响应速度显著提升，原生多模态（图像+文字），内置"语调适配层"。
- **国内开源力量**：阿里巴巴**通义千问（Qwen）**系列、清华与智谱合作的 **ChatGLM** 系列，中文能力强、社区活跃。

> 对智能体开发者而言：闭源模型提供"**开箱即用**"的便捷，开源模型赋予"**随心所欲**"的定制自由。

## 2.3 缩放法则与局限性（第 3.3 节）

### 2.3.1 缩放法则（Scaling Laws）

揭示模型性能与**参数量、训练数据量、计算资源**之间存在**可预测的幂律关系**。在对数-对数坐标系下，模型性能（通常用损失 Loss 衡量）与这三个因素都呈平滑的幂律关系——只要持续按比例增加，性能就会可预测地平滑提升，不会出现明显瓶颈。

**Chinchilla 定律（DeepMind, 2022）的重要修正**：在给定计算预算下，**模型参数量与训练数据量之间存在最优配比**。最优的模型应比之前认为的**更小**，但需要用**多得多的数据**训练。
- 例证：一个 700 亿参数的 Chinchilla 模型，由于使用了比 GPT-3（1750 亿参数）多 4 倍的数据训练，性能反而超越后者。
- 意义：纠正了"越大越好"的片面认知，强调**数据效率**，指导了 Llama 等高效大模型的设计。

**能力涌现（Emergent Abilities）**：当模型规模达到一定阈值后，会**突然**展现出小规模模型中完全不存在或表现不佳的全新能力。例如**链式思考（Chain-of-Thought）**、**指令遵循（Instruction Following）**、多步推理、代码生成，都是在参数量达数百亿甚至千亿级后才显著出现。
> 对智能体开发者的意义：**选择一个足够大规模的模型，是实现复杂自主决策与规划能力的前提**。

### 2.3.2 模型幻觉（Hallucination）

**定义**：模型生成的内容与客观事实、用户输入或上下文信息相矛盾，或生成了不存在的事实、实体或事件。本质是模型**过度自信地"编造"信息**，而非准确检索或推理。

**三种典型类型**：
- **事实性幻觉（Factual）**：生成与现实世界事实不符的信息。
- **忠实性幻觉（Faithfulness）**：在摘要、翻译等任务中，生成内容未能忠实反映源文本含义。
- **内在幻觉（Intrinsic）**：生成内容与输入信息直接矛盾。

**产生的多重原因**：
1. 训练数据中可能包含错误或矛盾信息。
2. 模型的自回归生成机制决定了它只是在**预测下一个最可能的词元**，**没有内置事实核查模块**。
3. 面对需要复杂推理的任务时，可能在逻辑链条中出错，从而"编造"错误结论。
> 例：一个旅游规划 Agent 可能推荐现实中不存在的景点，或预订航班号错误的机票。

**另外两个相关挑战**：
- **知识时效性不足**：模型知识来自训练数据，对收集日期之后的事件/概念/事实无法感知或正确回答。
- **训练数据偏见**：训练数据含人类社会偏见与刻板印象，模型会吸收并反映出来。

**缓解幻觉的三层方法**：

| 层面 | 方法 |
|---|---|
| **数据层面** | 高质量数据清洗、引入事实性知识、RLHF（人类反馈强化学习）——从源头减少幻觉 |
| **模型层面** | 探索新架构，或让模型能**表达对生成内容的不确定性** |
| **推理与生成层面** | ① **RAG（检索增强生成）**：生成前从外部知识库检索相关信息作为上下文，引导基于事实的回答（**目前最有效的方法之一**）；② **多步推理与验证**：每步进行自我检查或外部验证；③ **引入外部工具**：调用搜索引擎、计算器、代码解释器获取实时信息或精确计算 |

> 幻觉短期难以完全消除，但通过这些策略可显著降低其频率和影响。**这也是智能体必须引入"工具 + 检索"的根本动机。**

## 2.4 必须掌握 / 易踩的坑

- ✅ Transformer 核心组件：位置编码、多头注意力、掩码自注意力、交叉注意力、前馈网络、残差+层归一化。
- ✅ Decoder-Only 三大优势 + 自回归 + 因果掩码机制。
- ✅ 温度/Top-k/Top-p 的作用、分级、优先级与两个极端情况。
- ✅ Zero/One/Few-shot 的适用场景。
- ✅ BPE 三步 + WordPiece/SentencePiece 的差异。
- ✅ 缩放法则 + Chinchilla 定律 + 能力涌现。
- ✅ 幻觉的三种类型、多重成因与三层缓解方法。
- ✅ 模型选型的 8 个维度。
- ⚠️ **不要用字符数估算 Token**：中文 1 字 ≈ 1 token，英文 1 词 ≈ 1.3 token（第 9 章"1 token ≈ 4 字符"是缺 tokenizer 时的粗略兜底）。
- ⚠️ 采样参数不是越"确定"越好：全 0 温度容易让 Agent 陷入重复循环。
- ⚠️ 裸 `transformers` 不适合生产；生产用 VLLM/Ollama。
- ⚠️ 幻觉无法靠"提示词说不要幻觉"根治，要靠工具 + 检索 + 校验。
- ⚠️ 分词陷阱：`2+2` vs `2 + 2`、大小写差异，都会影响模型表现。

## 2.5 一页速查（Q&A 自测）

1. RNN 相比 N-gram 的进步与遗留问题？→ 能建模长距离依赖；但串行计算、无法并行、梯度消失。
2. Transformer 相比 RNN 的根本突破？→ 完全抛弃循环、依赖注意力，实现并行计算。
3. Decoder-Only 为什么成主流？→ 训练目标统一（预测下一个词）+ 结构简单易扩展 + 天然适合生成任务。
4. 因果掩码（掩码自注意力）解决什么？→ 训练时防止"偷看"未来词元，保证训练与生成一致。
5. 温度越大输出越怎样？→ 越多样、越发散，也越可能不连贯。
6. Top-k 与 Top-p 的区别？→ 固定截断数量 vs 按累积概率动态截断（对长尾更友好）。
7. 温度设 0 或 Top-k 设 1 会怎样？→ 其他采样参数变得无关紧要，输出确定。
8. 为什么不能直接用"单词"做输入单元？→ 词表爆炸 + 无法处理 OOV。
9. SentencePiece 的关键特点？→ 空格也是字符，可逆、语言无关。
10. 为什么分词影响成本与稳定性？→ API 按 Token 计费；同一文本不同分词器/语言 Token 数差异大；分词异常会让模型表现诡异。
11. Chinchilla 定律修正了什么？→ "越大越好"的片面认知，强调模型规模与数据量的最优配比。
12. 什么是能力涌现？对选型有什么启示？→ 规模达阈值后突然出现新能力；要选足够大的模型。
13. 幻觉的三种类型？→ 事实性、忠实性、内在幻觉。
14. 缓解幻觉最有效的推理层方法？→ RAG（检索增强生成）+ 多步验证 + 外部工具。
