## 11.1 项目一：智能旅行助手（多 Agent + MCP）

### 11.1.1 解决什么问题

把"搜景点、查天气、订酒店、算预算、排路线"这件原本要**几小时到几天**的事自动完成。传统方式三大痛点：**信息分散、缺少个性化、难以调整**。

### 11.1.2 四层架构（前后端分离）

```
前端层   Vue3 + TypeScript（表单输入、结果展示、地图可视化）
后端层   FastAPI（API 路由、数据验证、业务逻辑）
智能体层 HelloAgents（任务分解、工具调用、结果整合，含 4 个 Agent）
外部服务层 高德地图 API / Unsplash API / LLM API
```

**数据流**：用户在前端填表 → 后端验证数据 → 调用智能体系统 → 智能体依次调用景点搜索、天气查询、酒店推荐、行程规划 Agent → 每个 Agent 通过 MCP 协议调用外部 API → 整合结果返回前端 → 前端渲染展示。

**目录结构**：`backend/app/{agents, api, models, services, config.py}` + `frontend/src/{views, services, types, router}`。
**环境要求**：Python 3.10+、Node.js 16.0+、npm 8.0+。
**启动**：后端 `uvicorn app.api.main:app --reload`；前端 `npm run dev`（localhost:5173）；API 文档 `/docs`。

### 11.1.3 四 Agent 分工（本项目最值钱的部分）

| Agent | 职责 | 调用工具 |
|---|---|---|
| **AttractionSearchAgent** | 景点搜索 | `amap_maps_text_search` |
| **WeatherQueryAgent** | 天气查询 | `amap_maps_weather` |
| **HotelAgent** | 酒店推荐 | `amap_maps_text_search` |
| **PlannerAgent** | **信息整合** | **不调用任何外部工具**，输出严格 JSON |

**五步协作流程**：景点 → 天气 → 酒店 → 构建 planner 查询 → 解析 JSON。
PlannerAgent 的查询用 **f-string 组装**"用户需求 + 景点信息 + 天气信息 + 酒店信息"。

> **设计模式**：**"工具型 Agent + 纯整合型 Agent"分离**。末位 Agent 只消费结构化输入、生成结构化输出，保证最终结果的确定性与可控性。
> 原文金句："**能不能把复杂的任务分解成多个简单的任务，让不同的 Agent 各司其职？这就是多 Agent 协作的核心思想。**"

### 11.1.4 MCP 工具集成的三个工程要点

```python
MCPTool(
    name=...,
    command="npx",
    args=["-y", "@sugarforever/amap-mcp-server"],
    env={"AMAP_API_KEY": ...},
    auto_expand=True,       # 1 个 MCPTool 自动展开为 16 个独立 Tool
)
```

1. **底层是 stdio 的 JSON-RPC（`tools/call`），不是 HTTP**；npx 与 uvx 只是 JS/Python 生态之别。
2. **共享 MCP 实例**——在 `TripPlannerAgent.__init__` 中**只创建一次 MCPTool**，再 `add_tool(self.mcp_tool)` 给三个子 Agent。
   > 反例（原文明确）：每个 Agent 各建 MCPTool → **跑三个服务器进程、可能超过 API 速率限制、占用更多内存和 CPU**。
   > 原文金句："**更好的做法是让所有 Agent 共享同一个 MCPTool 实例。**"
3. **Unsplash 不封装成 Tool**——`UnsplashService` 直接在 API 路由里调用。
   > 原文："注意我们没有把 Unsplash 封装成 Tool 或 MCP 工具，而是直接在 API 路由中调用。……**图片搜索不需要 Agent 的智能决策，只是一个简单的数据增强步骤。**"

### 11.1.5 数据模型设计

**Pydantic 数据模型**：`BaseModel`、`Field`（`...` 表示必填、`ge`/`le` 范围验证、`default_factory=list`）、`Optional`、嵌套模型、`@field_validator(..., mode='before')` 自定义验证器（如把 `"16°C"` 解析为 16）。

**自底向上的模型设计**（第 13.2.4 节）：`Location` → `Attraction`/`Meal`/`Hotel` → `Budget` → `DayPlan` → `WeatherInfo` → `TripPlan`/`TripPlanRequest`。

**前后端同构类型**（第 13.2.5、13.5.2 节）：FastAPI 用 Pydantic 做请求/响应校验并自动生成 OpenAPI 文档；前端用 TypeScript `interface` 定义对应类型（`?` 对应 `Optional`）。

> ⚠️ 用字典承载业务数据的三个问题：字段名不统一（`lng`/`lon`/`longitude`）、无类型安全（运行时才报错）、维护性差。
> ⚠️ 外部 API 温度格式不规范 → 用 `field_validator` + `try/except` 容错返回 0。

### 11.1.6 前端工程细节

- **技术栈**：Vue 3 Composition API + `ref` + Ant Design Vue（`a-form`/`a-progress`/`a-statistic`/`a-menu`）。
- **API 服务封装**：`api.ts` 用 Axios 实例（baseURL、timeout 120000、请求/响应拦截器），`generateTripPlan` 是唯一 API 入口。
- **地图**：Result 页用 `@amap/amap-jsapi-loader` 打 Marker。

**预算计算（第 13.6.1 节）**：**在后端 PlannerAgent 提示词中要求 LLM 输出** `budget.total_attractions` / `total_hotels` / `total_meals` / `total_transportation` / `total`；前端 `v-if="tripPlan.budget"` 条件渲染 + `a-statistic` 展示。

**加载进度条（第 13.6.2 节）**：`setInterval` 每 500ms 递增（上限 90），按阈值切状态文案（搜索景点 → 查询天气 → 推荐酒店 → 生成行程计划），成功时置 100 并 `clearInterval`。
> 原文："如果用户点击'开始规划'按钮后，页面没有任何反馈，用户会以为系统卡住了，可能会刷新页面或重复点击。"

**行程编辑（第 13.6.3 节）**：`editMode` + `originalPlan` 双状态；进入编辑用 `JSON.parse(JSON.stringify(...))` **深拷贝**；移动用 ES6 解构交换 `[a,b]=[b,a]`，删除用 `splice`，保存后重新 `initMap()`。
> ⚠️ JS 对象是引用类型，编辑态必须深拷贝。

**导出（第 13.6.4 节）**：`html2canvas` 截 DOM → Canvas → `toDataURL()` 下载图片；PDF 走 `jsPDF('p','mm','a4')`，A4 宽 210mm 按宽高比算高度。
> ⚠️ `html2canvas` 处理嵌套 Canvas 有兼容性问题 + 高德 Canvas 跨域限制 → 教材给出 4 条替代方案（静态地图 API、分开导出后合并、Puppeteer 服务端截图、导出时隐藏地图），当前实现采用"**隐藏地图只导出文字**"。

**侧边导航（第 13.6.5 节）**：`a-menu` + `scrollIntoView({behavior:'smooth', block:'start'})`，各区块加 `id`。

### 11.1.7 关键踩坑

- SimpleAgent 每次 `run()` 只能执行一个工具，多次调用间要手工传中间结果；ReactAgent 虽能一轮多工具，但"**每一轮思考都需要调用 LLM**"且串行，时间成本高。
- 单 Agent 大提示词"**难以维护、容易出错、难以调试**"。
- **Axios 超时必须给足**（原文设 2 分钟），否则多 Agent + LLM + 外部 API 的 10-30 秒流程会被中断。
- Unsplash 是国外免费服务，"搜索结果可能不够准确"。

## 11.2 项目二：自动化深度研究智能体（TODO 驱动范式）

### 11.2.1 解决什么问题

面向"**知识密集型应用**"，让智能体自动完成研究任务。传统研究三痛点：**信息过载、缺少结构、重复劳动**。
核心价值：**节省时间**（"将 1-2 小时的研究工作压缩到 5-10 分钟"）、提高质量、可追溯、可扩展。

### 11.2.2 四层架构 + SSE 数据流

```
前端层   Vue3 + TypeScript（全屏模态对话框 UI、Markdown 结果可视化）
后端层   FastAPI（路由 /research/stream）
智能体层 HelloAgents（3 个 Agent：TODO Planner / Task Summarizer / Report Writer
                      + 2 个核心工具：SearchTool / NoteTool）
外部服务层 搜索引擎 + LLM 提供商
```

**8 步数据流**：用户输入 → 前端通过 **SSE** 连接 `/research/stream` → FastAPI 接收并创建研究状态 → 规划阶段分解 3 个子任务 → 逐个执行（SearchTool 搜索 → 调用总结 Agent → NoteTool 记录）→ 报告阶段整合 → SSE 流式返回 → 前端实时更新任务状态、进度条、日志、报告。

**目录结构**：`backend/src/{agent.py(核心协调器), main.py, models.py, prompts.py, config.py, services/{planner,summarizer,reporter,search}.py, workspace/}`；`frontend/src/{App.vue, components/ResearchModal.vue, composables/useResearch.ts}`。
**启动**：后端 `uv sync` 或 `pip install -e .` 后 `python src/main.py`（:8000）；前端 `npm run dev`（:5174）；`.env` 至少配 `LLM_PROVIDER`、`LLM_API_KEY`、`SEARCH_API`。整个研究约 1-3 分钟。

### 11.2.3 TODO 驱动的研究范式（本章灵魂）

**核心思想**："**将'研究'这个复杂任务转化为'规划→执行→整合'的流程。**"
**三要素**：智能规划器、任务执行器、报告生成器。

**三阶段流程**：
1. **规划（Planning）**：主题 → 3-5 个子任务，每个含 `title` / `intent` / `query` 三元组。
   > "一个好的规划器……将主题分解为 3-5 个子任务（**太少覆盖不全，太多会冗余**）。"
   > "**一个好的规划应该覆盖全面、逻辑清晰、查询精准、条目数量适中。**"
2. **执行（Execution）**：逐个 TODO 搜索 → 总结核心观点/关键数据/来源引用 [1][2] → 记录。
3. **报告（Reporting）**：按逻辑顺序整合，**消除重复的信息**并**保留所有来源引用**。

**三 Agent 职责划分**：
- **TODO Planner**：分解主题。
- **Task Summarizer**：提取核心观点/关键数据/来源引用 [1][2]。
- **Report Writer**：按逻辑顺序整合并消除重复。

**Prompt 关键设计点**：
- TODO Planner 提示词**注入当前日期**（`{current_date}`）以获取最新信息、明确要求**只返回 JSON**、给示例、约束子任务数量与逻辑关系。
- Report Writer 提示词规定**五段结构**：标题、概述（2-3 段）、各子任务详细分析（二级标题）、总结（1-2 段）、参考文献（按子任务分组）。

**协作模式**：**顺序协作**——线性流程、明确输入输出、无并发。`DeepResearchAgent.run()` 依次触发规划、执行（循环每个 TODO）、报告，并 `_emit_event` 推事件。

### 11.2.4 三个关键工程模式

**① ToolAwareSimpleAgent（可观测性监听器）**

```python
class ToolAwareSimpleAgent(SimpleAgent):
    """继承 SimpleAgent，重写 _execute_tool_call，新增 tool_call_listener 回调。"""
    def _execute_tool_call(self, tool_name, parameters):
        result = super()._execute_tool_call(tool_name, parameters)
        if self.tool_call_listener:
            self.tool_call_listener(
                agent_name=self.name, tool_name=tool_name,
                parsed_parameters=parameters, result=result)
        return result
```
三个 Agent 共用同一个监听器 → 统一记录 → 通过 SSE 推给前端。用途：**调试、日志、分析、进度展示**。

**② 服务层中介模式**

> "在这里我们没有采用往常一样的使得 simpleAgent 直接调用工具的形式，而是将 SearchTool 的执行结果通过**中间层**来返回给 Agent，这样会使得 Agent 更加专注处理得到的信息。"

四个服务：
- **PlanningService**：构建 Prompt、调 Agent、正则 `r'\[.*\]'`（`re.DOTALL`）提取 JSON、多策略回退、字段校验。
- **SummarizationService**：格式化来源、调 Agent、返回 `(总结, 来源URL列表)`。
- **ReportingService**：`_format_summaries` 拼装"任务N：标题 + 意图 + 总结 + 来源"。
- **SearchService**：调度引擎、去重、限 Token、错误降级、可选缓存。

**③ 搜索结果后处理三件套**
- `deduplicate_sources`：**按 URL 去重**。
- `limit_source_tokens`：默认 `max_tokens_per_source=2000`，按"**1 个 Token 约等于 4 个字符**"估算并截断加 `...`。
- **异常降级**：搜索异常时 `logger.error` 并 `return []`，不崩溃。
- 附加：**搜索缓存**（键 `md5(f"{query}_{max_results}_{search_api}")`，落盘 `./cache/search/*.json`）。

### 11.2.5 前端工程细节

- **真进度流（SSE）**：后端 `StreamingResponse(..., media_type="text/event-stream")` + `Cache-Control: no-cache` + `Connection: keep-alive`；事件类型 `progress` / `plan` / `task_summary` / `report` / `error` / `completed`；**进度算法 `10 + (idx/len(todo_items))*70`**，报告阶段 90，完成 100。
- 前端用 `marked`（`breaks: true`、`gfm: true`）渲染 Markdown。
- **全屏模态对话框 UI**：顶部栏/进度区域/内容区域/底部栏，支持 ESC 关闭、媒体查询响应式。

### 11.2.6 为什么这个范式好（第 14.7 节）

**可控性强**（流程固定）+ **质量可靠**（每步有明确输入输出）+ **易于调试**（每步可单独验证）+ **可扩展性好**（加 Agent 或换工具不影响主体）。

**其他要点**：
- **笔记持久化做断点续研**——"这些信息需要持久化到磁盘，以便在研究过程中断时能够从上次的进度继续。"（每个子任务一份 Markdown 笔记 `notes/{id}.md`，最终报告 `reports/final_report.md`）
- **配置化引擎切换**——`.env` 中 `SEARCH_API` / `LLM_PROVIDER` 等枚举配置决定后端行为，不改代码。
- **规划质量自评**——用数量区间、query 长度等规则给规划打分并给改进建议（`evaluate_plan`：数量 <3 扣分、>5 冗余、query 过短扣分）。
- **SearchTool 扩展**：DuckDuckGo / Perplexity / SearXNG + **Advanced 模式（组合多个搜索引擎）**；统一接口，返回 dict 含 `results`/`backend`/`answer`(仅 Perplexity)/`notices`。

## 11.3 项目三：构建赛博小镇（智能 NPC + 好感度系统）

### 11.3.1 解决什么问题

把智能体与**游戏引擎**结合，做"真正'活着'的 NPC"。传统 NPC 只能说固定台词或走预设对话树——"**虽然可控，但缺乏真正的'智能'和'生命力'**"。
**五大功能**：智能 NPC 对话、记忆系统（短期+长期）、好感度系统、2D 像素办公室中自由移动的游戏化交互、实时日志系统。

### 11.3.2 架构：游戏引擎 + 后端服务分离

```
前端层  Godot 4.5（游戏渲染、玩家控制、NPC 显示、对话 UI）
后端层  FastAPI（API 路由、NPC 状态管理、对话处理、日志）
智能体层 HelloAgents（每个 NPC 一个 SimpleAgent 实例，独立记忆与状态）
外部服务层 LLM API + Qdrant（向量库）+ SQLite
```

**数据流**：玩家在 Godot 中按 E 键与 NPC 互动 → Godot 通过 HTTP API 发送对话请求到 FastAPI 后端 → 后端调用 SimpleAgent 处理对话 → Agent 从记忆系统检索相关历史 → 调用 LLM 生成回复 → 后端更新 NPC 状态和好感度、记录日志 → 返回回复给 Godot 前端。

**Godot 侧结构**：`project.godot` + `scenes/{main,player,npc,dialogue_ui}.tscn` + `scripts/{main,player,npc,dialogue_ui,api_client,config}.gd` + `assets/{characters,interiors,ui,audio}`。
**后端结构**：`main.py`、`agents.py`、`relationship_manager.py`、`state_manager.py`、`logger.py`、`config.py`、`models.py`。
**环境**：Godot 4.2+、Python 3.10+；WASD 移动；日志在 `backend/logs/dialogue_YYYY-MM-DD.log`，`python view_logs.py` 实时查看。

### 11.3.3 五个核心机制

**① 短/长双层记忆**

```python
MemoryManager(
    working_memory=WorkingMemory(capacity=10, ttl_minutes=120),   # 保上下文
    episodic_memory=EpisodicMemory(db_path=..., collection_name=...)  # 保长期回忆
)
# 检索流程：短期取最近 5 条 → 长期 search(query, top_k=3) → 组成 context{recent, relevant}
# agent.run(msg, context=context) → add_interaction 写回
```

**② 好感度系统（LLM 定性打分 → 数值系统 → 驱动提示词）**

- **五级**：陌生(0-20)、熟悉(21-40)、友好(41-60)、亲密(61-80)、挚友(81-100)。
- 键为 `f"{npc_id}_{player_name}"`，记录 `score` / `level` / `interaction_count`。
- **增量逻辑**：用 LLM 分析对话判断玩家态度 → 友好 **+5** / 中立 **+2** / 不友好 **-3** → `max(-3, min(5, x))` 限制区间，异常默认返回 2（中立）；总分 `max(0, min(100, ...))`。
- **关键点**：按当前等级**动态改写 `system_prompt`**（`affinity_prompts` 五档文案），让回复风格随亲密度变化。
> "我们不能简单地让每次对话都增加固定的分数，这样会让系统显得机械和不真实。"
> "**好感度不仅仅是一个数字，它应该真正影响 NPC 的行为。**"

**③ 批量对话生成（轻负载模式）——性能核心**

把多个 NPC 的对话请求**合并成一次 LLM 调用**，用一个特殊提示词要求 LLM 一次性生成所有 NPC 的对话并返回 JSON（`{"张三": "...", "李四": "...", "王五": "..."}`）。
提示词含场景上下文（按时间自动推断）、NPC 信息、生成要求（每 NPC 一句话 20-40 字）、输出格式与示例。
> "一次 API 调用就能获得所有 NPC 的回复，**成本降低到原来的 1/3**，延迟也大幅减少。"

**混合模式：批量生成 + 即时响应**：后台 `background_dialogue_update()` 每 5 分钟（`asyncio.sleep(300)`）批量生成并缓存为 NPC 的"背景对话"；玩家按 E 键时切到 `/dialogue` 接口，调用该 NPC 专属 Agent 生成个性化回复。
> ⚠️ 边界：批量生成"更适合生成 NPC 的'**背景对话**'或'自言自语'，而不是与玩家的直接互动"。

**④ 状态机防并发**

```
/dialogue 九步流程：校验 NPC → 检查是否忙碌（is_busy，占用则返回 409）→ 标记忙碌
→ 取好感度 → 取带好感度等级的 Agent → 生成回复 → 更新好感度 → 记录日志
→ finally 释放忙碌标记
```
`StateManager` 维护 `npc_states`（位置 `{x,y}`、`is_busy`、`current_action`、`last_interaction`）——"这对于防止并发问题很重要，比如避免一个 NPC 同时与多个玩家对话"。

**⑤ 后端与 Godot 通信**

- **日志系统**：`DialogueLogger` **双输出**（控制台 + 文件），文件按日期命名 `dialogue_YYYY-MM-DD.log`，`log_dialogue` 记录 NPC/玩家/双方消息/好感度等级与分数/互动次数。
- **`api_client.gd`**：封装为 **AutoLoad 单例**；用 `HTTPRequest` 节点做异步请求，**用信号而非 await**——"这样可以让多个脚本同时监听同一个 API 响应"；为每个 API 创建独立 HTTPRequest 节点彼此不干扰；信号 `chat_response_received` / `chat_error` / `npc_status_received` / `npc_list_received`；请求前用 `get_http_client_status() != STATUS_DISCONNECTED` 跳过进行中的重复请求。
- **节点分组解耦**：`add_to_group("player"|"npcs"|"dialogue_system")` + `call_group` + 信号连接。
- **轮询 + 本地计时器**：`_process` 累加 `delta` 到阈值（默认 30 秒）才拉取一次状态，避免每帧请求。
- **UI 防重复提交**：请求期间 `editable=false` + `disabled=true`，响应回来再恢复并聚焦。

### 11.3.4 Godot 场景与节点（第 15.4.4、15.5 节）

- **节点是"乐高积木"**，父子树结构；**场景是一组节点保存为 `.tscn` 的"预制件"**，可嵌套实例化。
- 四个核心场景 Main / Player / NPC / DialogueUI；**三个 NPC 是同一个 `NPC.tscn` 的三次实例化**，只通过脚本参数区分角色。
- **Player 场景** = CharacterBody2D + AnimatedSprite2D + CollisionShape2D + Camera2D + InteractSound + RunningSound。
- **玩家控制**：`@export var speed`、`Input.get_vector(...)`、`move_and_slide()`、4 方向动画（缺失时回退 `walk` + `flip_h`）、`add_to_group("player")`、`_input` 监听 KEY_E/KEY_ENTER、交互时 `set_interacting(true)` 禁用移动。
- **NPC 行为**：`Area2D`（InteractionArea）`body_entered`/`body_exited` 检测玩家并 `player.set_nearby_npc(self)`；巡逻在出生点 ±`wander_range` 内随机选点，间隔 `randf_range(wander_interval_min, wander_interval_max)`；`update_dialogue()` 显示气泡并在 10 秒后隐藏。

**选择 Godot 的四点理由**：2D 开发天然优势、完全开源免费（MIT，对比 Unity 2024 运行时费用政策）、学习成本极低（GDScript 类似 Python）、与 Python 后端集成简单（内置 HTTPRequest）；局限是 3D 能力弱于 Unreal/Unity。

### 11.3.5 关键踩坑

- ⚠️ 多 NPC 并发对话 → LLM 请求并发、成本上升、可能因并发限制失败或延迟；解法是批量生成。
- ⚠️ NPC 被占用时必须返回冲突（409），并用 `finally` 释放忙碌标记。
- ⚠️ CORS `allow_origins=["*"]` 仅适合开发，生产要限制具体域名。
- ⚠️ 动画播放前要检查 `sprite_frames != null && has_animation(...)`；音效节点用 `get_node_or_null` 容错。
- ⚠️ AI NPC 三大挑战：**成本**（每次对话都调 LLM API）、**延迟**、**内容控制**（需设计好的提示词和内容过滤机制）。

## 11.5 ⭐ 33 条可复用工程模式（跨章汇总，建议直接抄进自己的项目）

### A. Agent 设计
1. **专家 Agent 拆分法**：按"输入 / 输出 / 所需工具"定义单职责 Agent（13.3.2）。
2. **"工具型 Agent + 纯整合型 Agent"分离**：末位 Agent 不持工具，只消费结构化输入产出结构化输出（13.3.2、13.3.3）。
3. **TODO 驱动范式**：任何开放式任务先拆成 3-5 个带 `title/intent/query` 的子任务，再逐个执行、最后整合（14.2.1）。
4. **服务层中介模式**：Service 负责构建 Prompt、调 Agent、解析结果、整理引用，**不让 Agent 直连工具**（14.5.1-14.5.4）。
5. **规划质量自评**：用数量区间、query 长度等规则给规划打分并给改进建议（14.5.1）。
6. **批量生成 + 即时响应混合**：高频低价值内容一次调用生成 N 份，高价值交互走专属 Agent 实时生成（15.2.4）。

### B. 工具与协议
7. **MCP 实例共享**：多 Agent 只创建一个 `MCPTool`（配 `auto_expand=True`）再各自 `add_tool`（13.4.3）。
8. **工具封装边界**：只有需要 Agent 自主决策的能力才封装为 Tool/MCP，纯数据增强直接放服务层/路由（13.4.4）。
9. **搜索结果后处理三件套**：URL 去重 + 单来源 Token 限制（2000 tokens，1 token≈4 字符）+ 异常降级返回空列表（14.4.1、14.5.4）。
10. **搜索缓存**：以 `md5(query_max_results_backend)` 为键落盘 JSON（14.5.4）。
11. **配置化引擎切换**：`.env` 中 `SEARCH_API` / `LLM_PROVIDER` 决定后端行为，不改代码（14.4.1）。
12. **工具调用可观测监听器**：加 `tool_call_listener` 回调，统一记录 agent/tool/参数/结果（14.3.2）。

### C. 输出与解析
13. **强制 JSON 输出的提示词写法**：明确"只返回 JSON，不要包含其他文本" + 示例输出 + 显式格式约束（14.3.1、15.2.4）。
14. **LLM 输出解析鲁棒化**：正则提取 + 多策略回退 + 必填字段校验（14.5.1）。
15. **强制 JSON 的降级**：`field_validator` + `try/except` 容错（13.2.4）。
16. **报告结构模板**：标题、概述、分节详细分析、总结、参考文献（按任务分组引用）（14.3.1）。
17. **来源可追溯**：总结阶段为每个观点加 [1][2] 标记，报告末尾汇总参考文献（14.2.2、14.4.2）。
18. **预算/成本类数值由 LLM 生成结构化 JSON 字段**，前端 `v-if` 可选渲染，不重复计算（13.6.1）。

### D. 状态、记忆与并发
19. **短/长双层记忆**：WorkingMemory（容量+TTL）保上下文，EpisodicMemory（向量检索 top_k）保长期回忆（15.2.1、15.2.3）。
20. **笔记持久化做断点续研**：每个子任务一份 Markdown 笔记，最终报告落 `reports/final_report.md`（14.4.2）。
21. **状态机防并发 + finally 释放**：`is_busy` 占用返回 409，处理结束在 `finally` 里复位（15.4.2）。
22. **数值化关系系统反过来驱动提示词**：情感分析 → 好感度增量（+5/+2/-3，钳制 -3~5，总分 0~100）→ 按五级动态改写 system prompt（15.3.2、15.3.3）。

### E. 前后端与 UI
23. **伪进度条**：长任务用 `setInterval` 按阶段文案递增（上限 90），成功再置 100 并清理定时器（13.6.2）。
24. **真进度流**：SSE（`text/event-stream` + `no-cache`/`keep-alive`）推 `progress/plan/task_summary/report/error/completed`；进度 `10 + idx/总数*70`（14.6.2）。
25. **前后端类型同构**：Pydantic 模型 ↔ TypeScript interface 一一对应，减少转换代码（13.2.5、13.5.2）。
26. **UI 层禁用输入防重复提交**：请求期间 `editable=false` + `disabled=true`，响应回来再恢复并聚焦（15.6.2）。
27. **信号驱动的异步 HTTP 客户端**：AutoLoad 单例 + 每接口独立 `HTTPRequest` 节点 + 用 signal 而非 await + 请求前检查连接状态（15.6.1）。
28. **轮询 + 本地计时器**：`_process` 累加 `delta` 到阈值（默认 30 秒）才拉一次状态，避免每帧请求（15.6.3）。
29. **节点分组与事件解耦**：`add_to_group` + `call_group` + 信号连接，组件松耦合（15.5.2）。
30. **模板化资产 + 参数实例化**：一份场景/预制件多次实例化，只改脚本参数（15.5.1）。
