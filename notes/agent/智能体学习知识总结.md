# Agent笔记

## 我对于Agent到底是什么的理解：agent = 大模型 + harness（也就是：一个循环 + 一个工具）

1. **一个大模型（LLM）**——负责"想"：读对话、做决策、生成文字或工具调用请求。
2. **一个循环（while True）**——负责"跑"：把模型的决策变成真实世界的动作，再把动作结果喂回去。
3. **一堆外挂机制**——权限、钩子、任务清单、子 agent、压缩、技能、记忆、系统提示……全部挂在循环的某个位置上，循环本身从头到尾没变过。

一条贯穿全部章节的观察：**核心循环三十行写完之后，后续所有机制都是"外挂"而不是"重构"。** 加工具改一行查表、加扩展改一行注册、加规划改一个计数器——循环的骨架（LLM 调用 → 追加回答 → 检查 tool_use → 执行工具 → 结果喂回）始终不变。

---

## 一、S01（Agent Loop）

### 1.1 循环的五步骨架

```
① messages = [用户问题]                 ← 起点
② 调用 LLM（带上消息历史 + 工具定义）     ← 想
③ 把模型回答追加进 messages
④ 回答里有没有 tool_use 块？
   ├─ 没有 → 循环结束，输出最终回答
   └─ 有   → 执行对应工具，结果作为 tool_result 追加 → 回到 ②
```

### 1.2 关键理解

- **循环的开关是"有没有工具调用"，不是"模型说了什么"。** 也就是判断stop_reason == tool_use?,是就继续，不是就停止
- **决策权在模型，执行权在 Harness。** 模型只能"请求"调工具（它生成的是一段 JSON 请求，不是真实执行），真正动手的是循环里的代码。模型够不到文件系统、shell、网络——它的一切现实影响力都经过 Harness。
- **tool_result 的角色是 user 消息。** 在 API 消息模型里，工具结果是以 user 角色回传的，配一个 `tool_use_id` 和发起请求的 `tool_use` 块一一对应。

## 二、S02（Tool Use）

### 2.1 为什么需要专用工具

只有一个 bash 工具时，模型"想读文件"却必须翻译成 `cat xxx`——想法和动作之间隔了一层字符串拼接，费 token、易出错、模型还没有文件是否存在的反馈。专用工具把"意图"和"操作"之间的翻译层去掉了。

### 2.2 工具的定义与实现

- **定义（schema）**：一份 JSON 描述，告诉模型"这个工具叫什么、接什么参数、干什么用"。模型只看得到这一层。
- **实现（handler）**：一个 Python 函数，真正干活的代码。模型永远看不到。

两者分离带来一个重要性质：**加一个工具 = schema 加一条 + 查表加一行映射，循环零改动。**

### 2.3 分发表（dispatch map）模式（也是我认为最有意思的）

```python
TOOL_HANDLERS = {"bash": run_bash, "read_file": run_read, ...}
output = TOOL_HANDLERS.get(block.name)(**block.input)
```

两个细节：

- 用 `.get()` 而不是 `[]`——模型请求了一个不存在的工具名时不会崩，而是返回一个错误字符串当结果喂回去，让模型自己纠正。
- `**block.input`——模型给的参数是字典，按名字展开成关键字参数。所以 **handler 的形参名必须和 schema 里的参数名完全一致**，这是隐式契约。

### 2.4 多工具调用

模型可以在一次回答里发出多个 `tool_use` 块（比如"读 A、读 B，然后总结"）。执行规则：

- 教学版按原始顺序**串行**执行。
- 每个结果用 `tool_use_id` 与请求配对，顺序错乱 = 配对错乱 = API 报错。
- 生产版的优化：把连续的"并发安全"调用切成批并行跑（读文件、glob 可以并行），遇到写操作或命令执行就单独串行。判断的不是"工具类型"而是"具体这次调用安不安全"（`ls` 可并发，`rm` 不可）。

### 2.5 路径校验

文件类工具在执行前做工作区约束：把相对路径拼到工作目录、resolve 成绝对路径、检查是否还在工作区内，越界就拒绝。

要点：**这个校验只护文件工具，不护 bash。** `bash` 里一条 `rm -rf /` 照样能跑——因为 bash 的参数是任意字符串，路径校验根本插不进手。这就是为什么后面必须有一层独立的权限系统。

### 2.6 结果落盘

工具输出可能巨大（比如读取一个超大文件）。生产做法是给每个工具设"结果上限"，超限就落盘成文件、模型只看到预览+路径。有个反直觉的特例：**读文件工具的结果不能落盘**，否则读文件→落盘→再读那个落盘文件→再落盘……无限循环。

## 三、S03（Permission）

- 定位：在"工具定义"和"工具执行"之间插一道**门**。每次调用先过门：直接放行（allow）、直接拒绝（deny）、还是停下来问人（ask）。
- 典型分级：读操作默认放行，写操作确认，危险命令（删文件、改系统）必须人工批准。
- 深层意义：权限检查本质上是"**人类对 agent 的控制面**"。模型的能力边界由工具定义决定，行为的边界由权限系统决定。
- 里面最重要的我认为就是三分批准法

## S04(Hooks)

### 4.1 解决的问题

如果要给循环加"日志、通知、审计、拦截"这些附加行为，最直觉的写法是往循环体里塞 if——塞十条之后循环就没法看了，而且每个扩展都绑死在循环代码里。

### 4.2 机制本体（两个函数）

```python
def register_hook(event, callback):    # 注册：事件名 → 回调列表
    HOOKS[event].append(callback)

def trigger_hooks(event, *args):       # 触发：按序执行回调
    for cb in HOOKS[event]:
        result = cb(*args)
        if result is not None:
            return result              # 有回调在干预 → 提前返回
    return None
```

循环只在固定位置"喊一声" `trigger_hooks("PreToolUse", ...)`，具体跑什么由注册表决定。新扩展 = 注册一行，循环代码不动。

### 4.3 四个标准事件

| 事件 | 触发时机 | 控制力 |
|---|---|---|
| UserPromptSubmit | 用户输入后、送入 LLM 前 | 观察 / 可注入内容 |
| PreToolUse | 工具执行**前** | **返回非 None = 拦截本次执行** |
| PostToolUse | 工具执行**后** | 观察（如大输出告警） |
| Stop | 循环退出**前** | **返回非 None = 强制循环继续** |

### 4.4 返回值即控制流

Hooks 机制的精髓我觉得在于返回值约定：回调返回 `None` 表示"我只是看看，不干预"；返回任何非 None 值都代表"我要干预"——PreToolUse 的干预是阻止，Stop 的干预是"不许结束，把这个返回值塞回对话继续跑"。

权限检查（s03）后来被重新表述为"一个 PreToolUse 钩子"——**机制升级不改循环，老的硬编码逻辑可以插件化**，这是 hooks 模式的价值示范。

### 4.5 运行痕迹里怎么认

日志里出现 `[HOOK] 事件名: ...` 行就是钩子在触发。每个用户输入前一条（UserPromptSubmit）、每次工具调用前一条（PreToolUse）、会话结束前一条统计（Stop）——看到这些行就能反推循环走到了哪个位置。

## S05（TodoWrite）

### 5.1 要解决的问题：注意力稀释

长任务里，工具结果不断涌入上下文，最初的计划被越冲越淡。十步的重构做到第三步，模型就开始"即兴发挥"——不是它忘了，是计划这个信息在上下文里的相对影响力下降了。

### 5.2 解法：把计划变成可读写的持久状态

给模型一个 `todo_write` 工具 + 一块内存中的任务列表。计划不再是"对话开头说过的一句话"，而是一个**随时可以读、可以改的状态物件**，每次更新都会渲染成清单重新进入上下文。

### 5.3 关键洞察

**todo_write 不给模型增加任何执行能力——它增加的是规划能力。** 模型该用的文件工具、命令工具一个没多；多出来的只是"一张随时能看能改的纸"。防走偏靠的是：计划常驻 + 遗忘提醒。

### 5.4 四条硬校验（状态容器自保护）

1. 单次更新最多 20 项——防止列表无限膨胀；
2. 每项 content 非空——防止占位垃圾；
3. status 只能是 pending / in_progress / completed——防止自由文本状态；
4. **同一时刻只允许一个 in_progress**——强制"一次只做一件事"的纪律。

输入解析的顺序也有讲究：先按 JSON 解析、失败再按 Python 字面量解析，**绝不用 `eval`**——模型输出是不可信输入，eval 等于把代码执行权交出去。

### 5.5 Reminder：主动对抗遗忘

连续 3 轮工具调用都没碰 todo_write，Harness 自动在工具结果里注入一条 `<reminder>更新你的任务清单</reminder>`，然后计数器清零。三个要点：

- 提醒不是给人看的，是**喂给模型的**；
- 它搭在 tool_result 上"顺风车"进上下文，不额外增加一轮调用；
- 计数器是循环局部变量，生命周期跟一次会话一致。

### 5.6 标准行为序列

列计划（全 pending）→ 领任务（改 in_progress）→ 完成（改 completed）→ 领下一个。观察一个 agent 是否有规划能力，看它的**第一次工具调用是不是建清单**即可。

## S06（Subagent）

### 6.1 要解决的问题：上下文污染

"重构整个模块"这类大任务，如果拆成十个子任务全在同一个对话里做，十个子任务的中间输出会把主对话淹没——主对话的价值是"记住总目标和全局决策"，不是堆放每个子任务的执行细节。

### 6.2 机制

- **派生**：主 agent 调一个 `task` 类工具，Harness 收到后创建一个**全新的空 messages 列表**，配上子任务描述和一个独立的（通常更精简的）子 system prompt。
- **独立生命周期**：子 agent 有自己的循环、自己的上下文、自己的工具集。主对话的噪音它看不到，它的执行细节也进不了主对话。
- **出口收敛**：子 agent 循环结束后，只把**最终文本回答**（不含中间过程）作为工具结果返回给主对话，通过 `tool_use_id` 配对汇合。
- **同步阻塞**：教学版主 agent 停在原地等子 agent 跑完。生产版有后台运行 + 通知的变体。

### 6.3 防套娃机制

子 agent 的工具集里**不含"再派子 agent"的工具**——否则子 agent 可以再生孙 agent，深度失控、资源爆炸。递归深度是 agent 系统必须显式设限的地方。

### 6.4 主/子对话的分界与汇合

分界 = `task` 工具被调用的那一刻（主 messages 冻结，新 messages 开辟）；汇合 = 子循环结束、最终文本经 `tool_result` 回到主 messages。看运行日志时：子 agent 的所有工具调用都发生在主对话"发起 task 调用"和"收到 tool_result"两个点之间。

## S07（Skills）

### 7.1 问题

多份规范文档（代码规范、审查清单、构建指南……）如果全部塞进 system prompt，每次调用都全量发送，但每次任务通常只用得上一份——无关文档白占 token，挤占真正需要的代码和对话空间。

### 7.2 解法：两段式加载

| 段 | 内容 | 进入位置 | 时机 |
|---|---|---|---|
| 第一段 | 技能名 + 一句话描述（**目录**） | system prompt | 启动时自动扫描 |
| 第二段 | 完整规范文档（**全文**） | tool_result | 模型主动调 `load_skill(name)` |

三个动作：**scan**（启动时扫目录、读每个 SKILL.md 的 frontmatter 建注册表）→ **catalog**（只把目录行写进 system prompt，并附一句"需要时用 load_skill 读全文"）→ **load**（按名查注册表返回全文；查不到则报错并列出可用技能）。

目录可能几百字，全文可能几万字——**常驻成本只有目录，按需才付全文的代价**。

### 7.3 为什么模型会主动去 load

因为 system prompt 里的目录明确告诉了它"有这些技能可用、用 load_skill 获取详情"。这是把"按需获取"变成模型的一个正常工具调用——**懒惰加载（lazy loading）通过工具化实现**。

## S08（Context Compaction）

### 8.1 为什么要压缩

上下文窗口有限且按 token 计费。对话越长：费用越高、响应越慢、且早期内容会被截断丢失。压缩的目标是在"省空间"和"保信息"之间找平衡。

### 8.2 两大类压缩（按是否调用 LLM 划分）

**1. 机械压缩（不调 LLM，零成本、零失真风险、纯规则）**

| 手段    | 做法 | 适用对象 |
|-------|---|---|
| 工具结果预算 | 每条 tool_result 超额就截断 | 长输出 |
| snip  | 老的中间消息替换成占位符，原文已落盘可查 | 历史消息 |
| micro | 逐条消息的局部瘦身（去空白、去冗余字段） | 每条消息 |
| 适配压缩  | 感知窗口将满时集中瘦身一轮 | 临时救急 |

**2. 摘要式压缩（要调一次 LLM）**

用一次额外的 LLM 调用把一大段历史浓缩成摘要文本，替换原文。触发阈值是消息条数超限（如超 50 条）。两个要点：

- 送给摘要模型的内容也要先裁剪——超长时**取头部一点+ 尾部一点**：开头含任务起点和系统决策，结尾含最新进展，中段细节最有牺牲价值。
- 这是整个压缩子系统里**唯一**需要 LLM 的地方。

### 8.3 怎么用运行痕迹验证压缩

这是本次学习中最重要的方法论收获之一：

- 机械压缩和摘要压缩的**落盘行为不同**：snip 写快照时消息数必然超过阈值，摘要压缩则正好在阈值上写。
- 统计所有快照的消息行数，**出现一个行数异于群体的孤立值**，就是摘要压缩发生过一次的铁证。
- 教训：**"日志里搜不到关键词"不等于"没发生"**——搜不到可能只是关键词不对；反过来，**异常值是最强证据**，因为它有唯一的原因解释。

## S10（System Prompt ）

### 10.1 定位

system prompt 是**给模型看的操作手册**：你是谁、在哪工作、有什么工具、有什么技能、遵守什么规则。它每轮调用都发送，是上下文里"性价比最高"的一段——少量 token 换取全程行为约束。

### 10.2 组装而非写死

生产做法是把 system prompt 拆成**多个段落（sections）**：身份段、环境段、工具段、技能目录段……按当前会话的真实状态动态拼装。依据是**真实状态**而不是关键词猜测——比如检测到工作区有 skills 目录才注入技能目录段，有记忆文件才注入记忆索引段。

### 10.3 缓存与指纹

组装结果要做缓存：内容没变就不重新组装。判断"变没变"的正确方式是**把完整内容序列化成字符串做指纹比对**（如 JSON dumps 后比较），而不是用内存地址相关的哈希——Python 的 `hash()` 对字符串每次进程启动会变（随机化），且内容相同的不同对象 hash 不保证可作持久指纹。这个细节是"序列化内容 vs 对象身份"的经典工程区分。

### 10.4 一个重要澄清

system prompt 的组装、技能目录的扫描、记忆索引的注入——**全是纯机械操作，零次 LLM 调用**。LLM 只消费组装结果。不要把"提示词里出现了技能信息"误解为"有个 LLM 参与了组装"。
